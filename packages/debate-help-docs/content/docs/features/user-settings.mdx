# User Settings

Gives a signed-in user a real settings page for debate style/font size/
color theme/light-dark-mode preferences, synced to their account, plus a
favorite-tools list.

- **Route:** `/settings`
- **Package:** `debate-round` (panel + validation + fetch client),
  `apps/debate-ai.com` (`/api/settings`, `user_settings` D1 table)

## What it shows

A form with Debate style/Font size/Color theme/Light-dark-mode pickers, a
Save button, and a "Favorite tools" section (starred from `/tools` or
managed here).

## Data flow

```
state/userSettings.ts / state/themeSettings.ts / state/favoriteTools.ts (pure validation)
round/user-settings-client.ts (fetch) → GET/PUT /api/settings
panels/UserSettingsPanel.tsx
components/theme-dropdown.tsx's useThemeState()
lib/hooks/useFavoriteTools.ts
```

## Known gaps

No optimistic-concurrency handling in general — two tabs editing the *same*
field at once has the last PUT win. `favoriteTools` no longer has this
problem: every code path that changes it (`toggleFavorite`/`removeFavorite`'s
single add/remove op, and `pruneUnknown`'s batch `removeFavoriteTools` op)
now resolves against the account's row as it stands at write time, not a
client-computed whole-list replace, so two tabs adding, removing or pruning
different entries at once can no longer drop each other's change. A plain
whole-list `favoriteTools` replace is still accepted by the route for a
caller that genuinely needs one, but nothing in the app sends one anymore.
Every other field (`debateStyle`, `colorTheme`, `wordLimitPresets`, etc.)
is still a plain whole-value replace with no such protection — low risk in
practice since each is normally edited from one open settings tab at a
time, but a real gap if that changes.
