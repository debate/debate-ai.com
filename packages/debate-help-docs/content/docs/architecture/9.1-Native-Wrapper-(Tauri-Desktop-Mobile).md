The `apps/debate-native-wrapper` project serves as the generic Tauri shell that packages the `debate-ai.com` site into native desktop and mobile applications. It provides a unified cross-platform container including platform profiles, native build configurations, icons, splash screens, build scripts, and Continuous Integration (CI) and release workflows specifically for the native wrapper app.

This ensures that users can run the Debate AI platform as a standalone native app on Windows, macOS, Linux desktops, and mobile devices (Android/iOS), while largely preserving the web app experience.

---

## Purpose and Scope

The primary function of the native wrapper is to present the existing web application inside a native container built using Tauri, providing a seamless desktop/mobile user interface and enabling closer OS integration.

- Wraps the main `debate-ai.com` site inside a secure Tauri WebView.
- Provides native icons, splash loading screens, and platform-specific configuration.
- Allows packaging and deployment as native apps for multiple OSes and mobile platforms.
- Facilitates native release pipelines and CI workflows for building and publishing.
- Handles specific authentication flow adaptations for OAuth providers like Google within native embedded webviews.

This page details its implementation, data/model flow, key configuration files, and workflows supporting the native wrapper packaging.

## Implementation Details

The native wrapper is a Tauri application that loads `https://debate-ai.com` in a WebView window. This leverages the full web app's UI and business logic without porting or rewriting, while the Tauri shell adds a native window, menu, icons, splash screen, build metadata, and native app packaging.

### Key Functional Components

- **WebView Loader:** The core of the wrapper is a WebView that displays the production `https://debate-ai.com` URL.
- **Native Wrapper Profiles:** These define platform-specific settings for Windows, macOS, Linux, Android, and iOS including icons, splash screen assets, and Tauri config options.
- **Tauri Configuration:** Located at `src-tauri/tauri.conf.json` or Rust-based config files managing app metadata, allowed URLs, permissions, and window parameters.
- **Build Scripts:** Scripts automate building the web app and then invoking Tauri packaging commands for desktop/mobile artifacts.
- **CI/Release Workflows:** GitHub Actions workflows validate, build, sign, and package native app binaries and mobile bundles.

### Google OAuth Handling in Embedded WebViews

An important caveat for embedded webviews in native apps is that many OAuth providers, especially Google, reject authentication flows within embedded browser engines due to security restrictions.

To work around this, the native wrapper:

- Replaces regular OAuth sign-in buttons in the native app with a **"Continue in your browser"** option.
- When clicked, initiates OAuth sign-in in the user's **default system browser**, external to the embedded webview.
- After successful OAuth, the system browser redirects using a **deep link URL scheme**: `debateai://auth-callback`.
- The native app captures this deep link and extracts a one-time auth token.
- The token is used by the wrapper to establish the authenticated session within the embedded WebView.

This flow is critical to enabling Google sign-in within the native wrapper despite browser restrictions.

### Camera and Microphone in the WebView

`getUserMedia` needs host-side setup in every WebView, or `navigator.mediaDevices` is missing and pages throw `undefined is not an object (evaluating 'navigator.mediaDevices.getUserMedia')`:

- **Linux (WebKitGTK):** media streams and WebRTC are off by default. `src-tauri/src/media.rs` turns them on for the main window.
- **macOS (WKWebView):** the bundle's `Info.plist` must carry `NSCameraUsageDescription` and `NSMicrophoneUsageDescription`. `scripts/configure.mjs` writes `src-tauri/Info.plist` from the profile (optional `mediaUsage.camera` / `mediaUsage.microphone` override the text), and `src-tauri/Entitlements.plist` adds the camera and audio-input entitlements a signed, hardened-runtime build needs.
- **All platforms:** the app's `on_permission_request` handler grants camera and microphone to the profile's sites (and their subdomains, HTTPS only) and the bundled offline build; anything else gets the WebView's default.

On the web side, the round webcam room calls `captureMedia` (in `packages/debate-round/src/webcam/useWebcamRoom.ts`), which turns a missing `navigator.mediaDevices` into a readable error.

## Configuration and Key Files

### `src-tauri/tauri.conf.json`

Defines crucial native app parameters:

- Application name, version, and description.
- URL whitelist configuring allowed navigation and resources for the WebView.
- Window dimensions and appearance.
- Icon and splash screen references for different platforms.
- Permissions and security policies.

### Profiles and Icons

Platform-specific build profiles hold customizations like:

- Icon sets for Windows `.ico`, macOS `.icns`, Linux `.png`.
- Splash screen SVG/PNG assets matching platform guidelines.
- Build targets tailored for desktop (x64, ARM) and mobile (Android/iOS) systems.

### Build and Release scripts

Typical build process:

1. Build the web app (`apps/debate-ai.com`) for production.
2. Run Tauri CLI commands (`tauri build`) to package native executables bundling the web assets or referencing the live site.
3. Generate platform-specific application bundles (.exe, .app, .deb, .apk, .ipa).
4. Sign and notarize builds if configured.
5. Upload artifacts or deploy to app stores.

## Known Limitations and Roadmap Notes

- **No Auto-Update System:** Automatic application update mechanisms are not currently implemented.
- **Mobile App Generation Partial:** Android and iOS native projects are scaffolded but lack fully tested end-to-end build and deployment workflows.
- **Mobile Camera Permissions:** Android `CAMERA`/`RECORD_AUDIO` and iOS usage descriptions are not added to the generated mobile projects yet.
- **Store Submission Status:** No current submissions to app stores; the apps are available mainly for direct installation from official builds.

These gaps are acknowledged and planned for future development.
