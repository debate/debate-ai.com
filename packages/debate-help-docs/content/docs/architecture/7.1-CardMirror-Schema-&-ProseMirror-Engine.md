The **CardMirror Engine** is the core of the REASON module in the Debate AI platform. It serves as a headless, framework-agnostic ProseMirror-based editor engine specialized for debate documents adhering to the Verbatim standard. The engine is responsible for defining a rich node and mark schema tailored to debate content, providing lossless round-trip interoperability with Microsoft Word `.docx` files and the native `.cmir` format. It also manages document repair, recovery, embedding containment, quick-card search, and reference PDF export capabilities.

---

## 1. CardMirror Node Hierarchy

The CardMirror schema enforces a strict, layered document structure reflecting debate document organization. This hierarchy ensures fidelity with competitive debating standards like Verbatim and Advanced Verbatim.

### Structural Levels

- **Pocket (Heading 1):** The top-level organizational unit, representing major thematic sections.
- **Hat (Heading 2):** A sub-section within a pocket.
- **Block (Heading 3):** A major argument grouping under a hat.
- **Card:** The fundamental logical unit containing structured evidence.

- **Tag (Heading 4):** The claim or summary statement of the card.
- **Cite:** The bibliographic source, typically styled with a bold 13pt style (`Style13ptBold`).
- **Body:** The main evidence text, supporting rich text marks (underline, emphasis, highlight).

This strict node layout follows the pattern:`pocket → hat → block → card → (tag, cite, body)`

## 2. ProseMirror Schema & Style System

The CardMirror schema is a specialized ProseMirror schema defining nodes and marks that replicate verbal debate document semantics in mutable rich-text form.

### Key Nodes and Marks

| Entity | Code Name | CSS Class | Role |
| --- | --- | --- | --- |
| Pocket | `pocket` | `.pmd-pocket` | Level 1 Outline (H1) |
| Hat | `hat` | `.pmd-hat` | Level 2 Outline (H2) |
| Block | `block` | `.pmd-block` | Level 3 Outline (H3) |
| Tag | `tag` | `.pmd-tag` | Level 4 Outline (H4) |
| Citation Mark | `cite_mark` | `.pmd-cite` | Bold/13pt bibliographic text |
| Underline Mark | `underline_mark` | `.pmd-underline` | Semantic evidence underline |
| Emphasis Mark | `emphasis_mark` | `.pmd-emphasis` | Bold + Underline "read" text |
| Highlight | `highlight` | `.pmd-highlight` | Highlighted text |

### Stable IDs and Bookmarks

To maintain persistent navigation and referencing, heading nodes (`pocket`, `hat`, `block`, `tag`) carry stable UUID `id` attributes. These IDs are used during DOCX export to generate Word Bookmarks with the prefix `pmd-heading-` for reliable cross-document anchoring.

- Function `ensureHeadingAnchor()` confirms or assigns such anchors on headings.
- This feature is critical for consistent referencing across sessions and export/import cycles.

## 3. OOXML / DOCX Pipeline

The engine provides robust interoperability with Microsoft Word `.docx` files, performing lossless import and export of Verbatim-styled debate documents with all structural and style semantics intact.

### Import/Export Data Flow

The core function `fromDocx` parses a `.docx` file into the ProseMirror schema in memory; the export process reverses this to generate a styled `.docx` preserving comments, numbering, and custom styles.

### Style Normalization

- The editor supports a **lossless Verbatim `.docx` round-trip**, allowing users to freely switch between Word and CardMirror formats without losing fidelity.
- Imported `.docx` files undergo **automatic style cleanup**, ensuring the imported document fits the schema model and removes extraneous Word-specific artifacts for consistent display and editing behavior.

## 4. Native `.cmir` Codec & Damage Recovery UI

The engine features a native `.cmir` format, a gzipped compressed JSON serialization of the full ProseMirror document state, enabling fast save/load cycles without DOCX round-trip overhead.

### Native Codec Workflow

- **Serialization:** Functions such as `serializeNative` and `serializeNativeAsync` convert the live document state into `.cmir` binary blobs.
- **Deserialization:**`parseNative` converts `.cmir` bytes back into document state, recovering stable node structures.
- **Doc Repair:**`parseNativeSalvage` attempts repair of corrupted `.cmir` data with heuristics and fallback strategies.
- **Read DocId Stamp:** The doc ID checksum supports verifying integrity and uniqueness.

### Crash-Recovery Sidebar

- The `RecoverySidebar` component provides a Word-like docked UI showing a list of unsaved or damaged drafts stored in a journaled browser storage [packages/debate-editor/src/editor/recovery-ui.ts1-169](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-editor/src/editor/recovery-ui.ts#L1-L169)
- Each draft row offers buttons to **Save** (to disk), **Open** (load in editor), or **Discard** (delete). The sidebar coexists with the editor UI, allowing iterative recovery.
- The sidebar mounts in the chrome host container, respecting embed containment [packages/debate-editor/src/editor/chrome-host.ts1-31](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-editor/src/editor/chrome-host.ts#L1-L31)

## 5. Chrome Host Container & Embed Containment

CardMirror's UI chrome (toolbars, ribbons, persistent modals) is designed to be embedded within larger host applications, such as the Debate AI platform's `/reason-editor` route or Flow's speech doc panel.

### Chrome Hosting Strategy

- The `chromeHost()` function returns the element inside which to mount the editor's permanent chrome.
- When embedded, `chromeHost()` returns the `.dec-cardmirror-root` container inside the host's `.dec-cardmirror-embed` element, ensuring all fixed-position elements are confined to the embed's bounding box rather than the full viewport.
- If not embedded, it falls back to `document.body` for full-window usage.
- This containment prevents editor chrome from obscuring host UI components like sidebars.

### Embed Containment CSS

- The `.dec-cardmirror-embed` container is styled with `position: relative` and confines all permanent chrome overlays via descendant selectors.
- Fixed-position floaters like tooltips remain `position: fixed` relative to viewport for coordinate correctness.
- This architecture supports embedding multiple editors or UIs on different parts of a page seamlessly.

## 6. Quick Card Search & Editor Settings

### Quick Card Search

The editor includes a fast, floating command-palette-style Quick Card search bar with a prefix system supporting different search scopes:

| Prefix | Search Scope | Behavior |
| --- | --- | --- |
| `q ` | Quick cards only | Filters to cards in the quick card store |
| `d ` | Dropzone only | Searches temporary drag-drop "dropzone" buffers |
| `c ` | Ribbon commands | Searches command palette actions |
| `s ` | Settings | Searches editor settings categories and options |
| `f ` | `.cmir` files | Searches file-level or intra-file objects |
| `t ` | Workspace links / tools | Navigates to other app tools/panels |
| None | All sources (after typing) | Comprehensive search; no empty query browsing |

The search handlers integrate with a warm cache storing parsed file documents to optimize frequent searches and avoid re-parsing.

- The cache maps file paths to parsed PMNode docs, objects, and outlines keyed by modification time.
- Pins and auto-pins (such as recent files) determine which entries are kept warm and pruned.

The search results can insert content blocks into the editor via the `insertSpeechSlice` method, which snaps inserts cleanly to block boundaries, preserving document integrity.

### Editor Settings UI

- CardMirror preferences (general, appearance, accessibility) are exposed via a React component `CardMirrorPreferencesPanel` embedded in the main app's settings page on `/settings`.
- This panel loads the editor's native settings UI as a same-origin iframe to isolate heavy stylesheet and maintain style encapsulation.
- The iframe self-sizes dynamically using postMessage events.
- Editor settings include color palettes, typography controls, accessibility overrides, and performance benchmarks.
- Preferences persist to the user's account on sign-in.

## 7. Reference PDF Export

The engine includes functionality to export the keyboard-shortcut reference as a paginated, print-ready PDF file.

- The `buildShortcutsReferencePdf()` function constructs the PDF layout using `pdf-lib`, embedding Helvetica fonts and rendering all shortcut groups and rows with clear typographic hierarchy and gutters [packages/debate-editor/src/editor/reference-pdf-export.ts1-93](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-editor/src/editor/reference-pdf-export.ts#L1-L93)
