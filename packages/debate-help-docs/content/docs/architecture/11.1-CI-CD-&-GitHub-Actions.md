This section documents the automated integration and delivery pipelines for the Debate AI platform. The repository utilizes GitHub Actions to manage Pull Request (PR) lifecycles, specifically focusing on automated merging for trusted contributors and AI-driven development agents like Claude, and the automated release process for the `debate-api-client` package.

## Automated PR Management

The core of the repository's CI/CD strategy for PR management is the `auto-merge-claude.yml` workflow. This workflow is designed to streamline the contribution process by automatically approving and merging PRs that meet specific criteria, thereby reducing manual overhead for routine updates or AI-generated improvements.

### Workflow: Auto-merge Claude PRs

The workflow is triggered by `pull_request` events, specifically when they are `opened`, `synchronize`, `reopened`, or `closed`[[.github/workflows/auto-merge-claude.yml:3-5]](). It operates with elevated permissions to write repository contents and manage pull requests [[.github/workflows/auto-merge-claude.yml:7-9]]().

#### Actor Filtering

The workflow only executes the `auto-merge` job if the PR is not a draft and the author (`github.actor`) is one of the following trusted entities:

- `claude[bot]`[[.github/workflows/auto-merge-claude.yml:23]]()
- `anthropic-claude[bot]`[[.github/workflows/auto-merge-claude.yml:24]]()
- `vtempest` (Repository Maintainer) [[.github/workflows/auto-merge-claude.yml:25]]()

#### Automation Logic

The `auto-merge` job follows a three-step execution pattern:

1. **Auto-approve**: Uses `hmarr/auto-approve-action@v4` to provide an official approval on the PR [[.github/workflows/auto-merge-claude.yml:27-30]]().
2. **Wait for Checks (Polling)**: A custom bash script polls the GitHub API via the GitHub CLI (`gh pr view`) to check the `statusCheckRollup`[[.github/workflows/auto-merge-claude.yml:48-54]]().

- **Self-Filtering**: The script explicitly filters out its own workflow name (`SELF_WORKFLOW`) from the check list to avoid infinite waiting [[.github/workflows/auto-merge-claude.yml:37, 55-56]]().
- **Failure Detection**: If any check returns `FAILURE`, `TIMED_OUT`, `CANCELLED`, `ACTION_REQUIRED`, `STARTUP_FAILURE`, or `ERROR`, the workflow exits with an error [[.github/workflows/auto-merge-claude.yml:58-64]]().
- **Timeout**: The polling loop times out after 30 minutes [[.github/workflows/auto-merge-claude.yml:38, 73-76]]().
3. **Squash and Merge**: Once all other checks are `COMPLETED` with successful conclusions, the PR is merged using `gh pr merge`[[.github/workflows/auto-merge-claude.yml:89-90]]().

### Branch Cleanup

To maintain repository hygiene, a secondary job `delete-branch` is defined. This job triggers when a pull request is `closed` and the `merged` status is `true`[[.github/workflows/auto-merge-claude.yml:92-97]](). It uses the GitHub API via `gh api` to explicitly delete the head branch reference from the repository's git refs [[.github/workflows/auto-merge-claude.yml:99-102]]().

## Branch Protection & Strategy

While the `auto-merge-claude.yml` file handles the execution of merges, it implements logic to respect and interact with GitHub's branch protection mechanisms:

| Feature | Implementation Detail |
| --- | --- |
| **Merge Strategy** | Squash and Merge is enforced via `gh pr merge --squash`[[.github/workflows/auto-merge-claude.yml:89]](). |
| **Auto-Merge Fallback** | If a direct merge is blocked (e.g., by settling branch protections), the workflow uses the `--auto` flag to enable GitHub-side auto-merge [[.github/workflows/auto-merge-claude.yml:90]](). |
| **Permissions** | The workflow requires `contents: write` and `pull-requests: write` to perform approvals and merges [[.github/workflows/auto-merge-claude.yml:7-9]](). |
| **Check Validation** | The polling logic ensures that external CI checks (e.g., build, lint, test) have a successful `conclusion` before proceeding [[.github/workflows/auto-merge-claude.yml:58-60]](). |

## `npm-release.yml` for `debate-api-client`

The `npm-release.yml` workflow automates the publishing of the `debate-api-client` package to npm. This is the only package in the monorepo that is publicly published; all other workspace packages are marked as `"private": true`[[packages/debate-api-client/README.md:57]]().

### Workflow Trigger and Permissions

The workflow is triggered by two events:

- **Push to Tag**: When a tag matching `debate-api-client@*` is pushed to the repository. The `*` wildcard allows for version tags like `debate-api-client@0.1.0`[[.github/workflows/npm-release.yml:5-6]]().
- **Workflow Dispatch**: Manually via `workflow_dispatch`, allowing for an optional `tag` input to specify the npm dist-tag (defaulting to `latest`) [[.github/workflows/npm-release.yml:8-12]]().

It requires `contents: read` and `id-token: write` permissions, with `id-token: write` being crucial for OIDC-based authentication with npm for provenance [[.github/workflows/npm-release.yml:14-15]]().

### Publish Job Steps

The `publish` job runs on `ubuntu-latest` and sets the working directory to `packages/debate-api-client` for all subsequent `run` commands [[.github/workflows/npm-release.yml:24-28]]().

1. **Checkout Code**: Uses `actions/checkout@v4` to clone the repository [[.github/workflows/npm-release.yml:29-30]]().
2. **Set up Bun**: Installs Bun using `oven-sh/setup-bun@v2`[[.github/workflows/npm-release.yml:32-35]](). Bun is used for dependency installation, type-checking, testing, and building.
3. **Set up Node**: Installs Node.js using `actions/setup-node@v4` and configures npm with the registry URL and `NODE_AUTH_TOKEN` for publishing [[.github/workflows/npm-release.yml:37-41]]().
4. **Install Dependencies**: Runs `bun install --ignore-scripts` in the monorepo root to install all dependencies [[.github/workflows/npm-release.yml:43-45]]().
5. **Type-check**: Executes `bun run typecheck` within the `debate-api-client` package. This step involves regenerating types from `debate-openapi.yml` using `@hey-api/openapi-ts` and then running `tsc --noEmit`[[packages/debate-api-client/package.json:46-47]]().
6. **Run Tests**: Executes `bun run test` to run the package's tests using Vitest [[.github/workflows/npm-release.yml:50-51]](), [[packages/debate-api-client/package.json:48]]().
7. **Build**: Executes `bun run build`. This command first regenerates types and then compiles the TypeScript code to JavaScript using `tsc -p tsconfig.build.json`[[.github/workflows/npm-release.yml:53-54]](), [[packages/debate-api-client/package.json:46]](). The generated types and compiled JavaScript are placed in the `dist/` directory [[packages/debate-api-client/package.json:35]]().
8. **Verify Package Version Matches Tag**: If the workflow was triggered by a `push` event (i.e., a tag push), this step compares the version extracted from the Git tag (`GITHUB_REF_NAME`) with the `version` field in `package.json`[[.github/workflows/npm-release.yml:57-64]](). If they do not match, the workflow fails.
9. **Publish to npm**: Finally, `npm publish --access public --provenance --tag "${{ github.event.inputs.tag || 'latest' }}"` is executed. The `--provenance` flag ensures that the published package includes provenance information, enhancing supply chain security. The `--tag` argument uses the input from `workflow_dispatch` or defaults to `latest`[[.github/workflows/npm-release.yml:66-70]]().

### `debate-api-client` Generation and Structure

The `debate-api-client` package provides a typed SDK for the Debate AI API.

- It is generated from the OpenAPI specification `apps/debate-ai.com/public/debate-openapi.yml`[[packages/debate-api-client/README.md:4]]().
- The generation uses `Hey API` (`@hey-api/openapi-ts`) to create request/response types in `src/generated/`[[packages/debate-api-client/README.md:46-47]](), [[packages/debate-api-client/openapi-ts.config.ts:1-13]]().
- The actual SDK functions (`src/sdk.ts`) and the HTTP client (`src/client.ts`) are hand-written on top of these generated types. The client uses `grab-url` for HTTP requests, providing features like caching, retries, rate limiting, and request deduplication [[packages/debate-api-client/README.md:4-7]](), [[packages/debate-api-client/README.md:47-49]](), [[packages/debate-api-client/src/client.ts:80-83]]().
- The `createClient` function allows configuring a client instance with a `baseUrl`, `headers`, and `grab` options [[packages/debate-api-client/src/client.ts:84-116]](). A shared default client is also exported, pointing to `https://debate-ai.com/api`[[packages/debate-api-client/src/client.ts:119]]().

# Additional Notes on Issue Templates and PR Management Patterns

Supplementing the CI/CD workflows are GitHub issue templates which provide a standard structure for bug reports and feature requests to maintain quality and reproducibility. The templates reside in `.github/ISSUE_TEMPLATE/bug.md` and `.github/ISSUE_TEMPLATE/feature_request.md` and enforce fields such as:

- What happened and expected behavior
- Steps to reproduce
- Environment details
- Relevant logs

This standardized issue management reduces triage overhead and improves automated labeling and routing.
