This section documents the Progressive Web App (PWA) implementation for the Debate AI platform. The system uses a custom service worker to provide offline support, resource caching, and a native-like app installation experience. Key elements include asset versioning, caching strategies, error handling, and debug instrumentation to ensure resilient offline usage.

## Overview & Metadata

The PWA uses a standard web manifest and metadata to enable cross-platform compatibility and native app behavior when installed.

### Web Manifest & Assets

- The `site.webmanifest` file configures the app's identity and behavior:

- `name`: "Debate AI"
- `display`: `"standalone"` for a native app appearance without browser UI
- `start_url`: `/` as the entry point
- Multiple icon sizes (192px, 512px) for various device resolutions
- Asset list (`APP_FILE_LIST`) includes fonts, JS/CSS bundles, icons, and static images [apps/debate-ai.com/lib/offline-sw/app-file-list.ts1-147](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/lib/offline-sw/app-file-list.ts#L1-L147)

| Property | Value | Description |
| --- | --- | --- |
| `name` | "Debate AI" | Full app name |
| `display` | `standalone` | Removes browser chrome for a native look |
| `icons` | PNG 192/512 | App icons for installable homescreen |
| `start_url` | `/` | Initial app URL when launched from homescreen |

## Service Worker Implementation

The service worker (SW) orchestrates caching, resource fetching, and update processes using a version-based cache naming scheme and differentiated caching strategies.

### Build & Versioning

- A build script `lib/offline-sw/generate.cjs` scans the build output directory `dist/client` to list all cacheable assets and generates:

- `app-file-list.ts`: a stable list of versioned assets to precache.
- `version.ts`: a derived `VERSION` string combining the package version and a hash digest of build assets.
- This versioning scheme ensures that every distinct build gets a unique cache and that old caches are purged on activation [apps/debate-ai.com/lib/offline-sw/generate.cjs6-73](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/lib/offline-sw/generate.cjs#L6-L73)
- Example version: `0.9.0-f880f8dc0d4f`[apps/debate-ai.com/lib/offline-sw/version.ts1](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/lib/offline-sw/version.ts#L1-L1)

### Service Worker Lifecycle & Cache Management

The core SW logic is implemented in TypeScript (`service-worker.ts`) and compiled to `public/service-worker.js`[apps/debate-ai.com/lib/offline-sw/service-worker.ts1-215](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/lib/offline-sw/service-worker.ts#L1-L215)

- **Cache name**: `debate-ai-${VERSION}` isolates each build cache.
- **Install event**:

- Calls `skipWaiting()` to immediately take control.
- Opens the versioned cache, then precaches `/` plus all files listed in `APP_FILE_LIST`.
- Attempts to cache assets individually so failures in one do not abort the whole install.
- **Activate event**:

- Deletes all old caches not matching the current version.
- Calls `clients.claim()` to immediately control pages.
- **Fetch event**:

- Intercepts all `GET` requests on the origin.
- Applies caching strategy based on the request type.

## Caching Strategies & Data Flow

### Network-First vs Cache-First Strategy

The PWA service worker distinguishes between dynamic and static content, applying appropriate caching policies:

| Content Type | Strategy | Purpose |
| --- | --- | --- |
| Documents (HTML/RSC payloads), API requests | **Network-First** | Fetch latest data; use cache only offline fallback. Ensures fresh content and prevents stale RSC/HTML mix. |
| Static assets under `/assets/` and listed in `APP_FILE_LIST` (JS bundles, CSS, fonts, images) | **Cache-First** | Load instantly from cache for performance and offline availability; update cache asynchronously. |
| Speculative requests (prefetches) | No response from SW | Let browser handle to avoid caching aborted/failing prefetches causing broken navigation later. |

#### Detailed Logic

- `isDocumentRequest(request, url)`:

- Returns true for navigation requests, or those with `Accept` headers for `text/html` or `text/x-component`, or RSC-specific URL patterns (`.rsc` extension or `_rsc` query param).
- `isImmutableAsset(url)`:

- True if the URL path starts with `/assets/` or is in the precached list (`PRECACHED`).
- `isSpeculativeRequest(request)`:

- Detects browser speculative prefetches via headers `Sec-Purpose: prefetch` / `Purpose: prefetch` or non-navigation document prefetch.
- `isNavigationRequest`:

- Detects navigations specifically through fetch event requests.

**Sources:**

- [apps/debate-ai.com/lib/offline-sw/service-worker.ts131-166](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/lib/offline-sw/service-worker.ts#L131-L166)

### Explanation

- **Network-First**: Applied to HTML documents, RSC payloads, and API routes (`/api/*`). The SW tries to fetch from network first to get fresh data. On failure (e.g., offline), it falls back to cache.
- **Cache-First**: Applies to static, immutable assets on the same origin under `/assets/` or listed in precache. The SW serves directly from cache and fetches to update cache if missing or stale.
- **Speculative requests**: The SW declines to handle them to avoid caching failures that would poison future navigations.

### Cache Put Safety

Cache updates use `cache.put()` wrapped in `try/catch` to avoid unhandled errors or request failures interrupting the fetch flow.

### Fallback Shell

If network and cache both fail on a navigation, the SW attempts to serve the root HTML document `/` cached during install. This provides an offline fallback shell to support offline navigation.

## Service Worker Registration on Client

The SW is registered from a client React component `ServiceWorkerRegistrar` which runs once on app startup:

- Checks for service worker support in the browser.
- Skips registration on localhost for development.
- Registers `/service-worker.js` from the public directory.
- Logs registration success or errors using the `debugLog` facility for opt-in debug visibility [apps/debate-ai.com/components/layout/ServiceWorkerRegistrar.tsx1-40](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/components/layout/ServiceWorkerRegistrar.tsx#L1-L40)

This component is mounted in the root layout so the SW is active on every page load outside localhost development.

## Error Boundary & Debug Logging Integration

While the PWA’s service worker handles fetch failures gracefully with caching fallbacks, React-level error boundary components such as the global `app/error.tsx` (not shown here) handle runtime client errors gracefully.

The `debugLog` utility [apps/debate-ai.com/lib/debug-log.ts](https://github.com/debate/debate-ai.com/blob/34937310/apps/debate-ai.com/lib/debug-log.ts) offers developers a quiet way to log verbose state and flow information:

- Active in development mode or opt-in via `localStorage.setItem("debate-ai:debug", "1")`.
- Used across client components, including service worker registrar and auth hooks.
- Avoids polluting user consoles while enabling detailed diagnostics on demand.
