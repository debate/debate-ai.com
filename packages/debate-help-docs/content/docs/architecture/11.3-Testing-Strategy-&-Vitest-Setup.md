This page details the testing strategy employed in the `debate-ai.com` monorepo, focusing on the Vitest setup for unit and integration tests. It covers the root Vitest configuration, how individual packages define their test configurations, the conventions for organizing test files, and the approach to testing stateful and pure-logic modules.

---

## Vitest Configuration

The monorepo uses [Vitest](https://vitest.dev/) as its testing framework. A central `vitest.config.ts` file at the project root defines the overall testing strategy, including how projects are discovered and code coverage is reported.

### Root `vitest.config.ts`

The root `vitest.config.ts` is located at `apps/debate-ai.com/vitest.config.ts`[vitest.config.ts1-56](https://github.com/debate/debate-ai.com/blob/34937310/vitest.config.ts#L1-L56) Key points of this configuration include:

- **Project Discovery**:

- All packages under `packages/*` are registered as distinct Vitest projects, enabling running tests across the monorepo with a single command.
- Explicitly excludes:

- `packages/README.md` — not a package directory.
- `packages/debate-help-docs` — it is a documentation site (Fumadocs/Next.js) and has no test folder.
- Additionally, the web app at `apps/debate-ai.com` has no test folder under its root but contains plain Node.js libraries in `apps/debate-ai.com/lib` which have tests registered inline in the root Vitest config.
- **Coverage Reporting**:

- Uses the `"v8"` coverage provider.
- Reports coverage in `text`, `lcov`, and `html` formats.
- Coverage output directory is `coverage` at the repo root.
- Coverage includes all source files matching `packages/*/src/**/*.{ts,tsx}` but excludes typings (`*.d.ts`), `node_modules`, any `test` folders, and data/schema assets under `packages/debate-data-sync`.
- This enables aggregation of coverage across all packages into one combined report.

This overall Vitest setup means commands like `npm test` or `npx vitest run` executed from the repo root or `apps/debate-ai.com` run all tests across all packages. Likewise, coverage can be generated combined across packages for upload to Codecov.

## Codecov Configuration

The repository uses a centralized Codecov configuration file at `codecov.yml`[codecov.yml1-151](https://github.com/debate/debate-ai.com/blob/34937310/codecov.yml#L1-L151) to manage coverage reporting and quality gates.

Key highlights:

- The coverage data is produced by running `npm run coverage` which in turn runs all `test/` suites for packages through Vitest and outputs a single merged coverage file at `coverage/lcov.info`.
- Coverage thresholds and precision settings ensure the project coverage target is dynamic (`auto`) with allowances for minor fluctuation (`threshold: 2%` informational).
- Patch-level thresholds require at least 60% coverage with a 5% tolerance, to enforce coverage on new or changed code.
- Flags are defined per package (e.g., `debate-api-client`, `debate-round`, etc.) to attribute which package contributes to coverage gains or losses.
- Each package is also declared as an individual "component" for separate status reporting. This enables granular coverage visibility in the Codecov UI.

This precise per-package segmentation helps contributors identify test coverage impact scoped to their packages without noise from unrelated code.

## Per-Package Vitest Configurations

While the root `vitest.config.ts` manages most common settings and discovery, individual packages can define their own `vitest.config.ts` for specialized needs such as:

- Custom test environment (e.g., Node vs DOM)
- Package-specific setup or teardown scripts
- Mocks or aliases relevant only within that package
- Different include/exclude patterns

Packages are encouraged to keep tests under their own `test/` directories organized by feature or module, allowing the root config to automatically pick them up by project globs.

## Test Directory Conventions

Each package contains a `test/` folder at the root of its source tree to hold unit and integration tests. This segregation enforces a clear boundary between production source and test code.

For example:

- `packages/debate-round/test/live-update.test.ts` tests cross-tab synchronization logic in `live-update.ts`[packages/debate-round/test/live-update.test.ts1-149](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-round/test/live-update.test.ts#L1-L149)
- `packages/debate-round/test/panels.test.tsx` tests React UI components related to the round workspace [packages/debate-round/test/panels.test.tsx1-91](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-round/test/panels.test.tsx#L1-L91)

This convention aids:

- Discoverability for Vitest's project-based test runs
- Maintainability by grouping related tests by domain
- Separation of concerns, avoiding test code intermingling with production logic

## Testing State and Pure-Logic Modules

The testing strategy distinguishes between pure-logic modules (stateless, functional code) and stateful or UI components.

### Pure-Logic Modules

Modules containing pure functions, helpers, or business logic are tested directly with normal unit tests. These tests:

- Import code under test explicitly
- Use Vitest's `describe` and `it` to organize the cases
- Use assertions to verify expected outputs and edge cases

For instance, `packages/debate-round` includes `live-update.ts`, which exports functions like `isFlowLiveUpdateStorageEvent` that determine if a `StorageEvent` should trigger a UI update.

Example test excerpt:

This style cleanly ensures utility correctness without coupling to React or UI.

---

### Stateful Components and Panels

For React components and panels that maintain or display state, the testing approach includes:

- **Render Tests**: Render React components to static markup strings using `renderToStaticMarkup` from `react-dom/server`. This lets tests verify the output HTML structure and content easily.
- **Prop-Driven Testing**: Components are tested as pure render functions driven by props, allowing easy injection of test data and mocks.
- **Integration with Logic Modules**: Components that rely on business logic functions or hooks use mock data aligned to those modules' output shapes.
- **Specific UI Assertions**: Tests assert presence or absence of key UI elements, text content, and expected conditional behavior.

For example, `SharedFlowSyncPanel` in `packages/debate-round` is a React component that displays the shared flow sync experience. It integrates multiple logic slices to merge edits, compute conflicts, and poll for sync and presence status.

**Title: SharedFlowSyncPanel Testing Flow**

Tests verify that:

- The panel renders a "Shared Flow Sync" title
- Conflict warnings (e.g., "Conflicts") appear given colliding edits
- Editors' names appear in the conflict list
- Status messages like "Live sync off" appear as expected

This approach validates both UI rendering and integration with state/logic.

## Summary

- The root `vitest.config.ts` centrally manages all Vitest projects for all packages.
- Coverage is aggregated and reported to Codecov with fine-grained package flags.
- Tests reside under `test/` per-package following consistent structure.
- Pure logic is tested deeply and directly with unit tests.
- Stateful React components use static render testing driven by mock props and logic outputs.
- This layered approach balances test reliability, performance, and maintainability across the monorepo.
