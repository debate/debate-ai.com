The Ebb Flow Editor integrates a local-first, peer-to-peer collaboration protocol with a specialized loopback bridge to consume evidence directly from the CardMirror research editor. This wiki page provides an in-depth technical overview of the CRDT replica and operations model, the peer link transport abstraction for collaboration, the handshake and presence protocols, conflict-free merge strategies, and the CardMirror Bridge protocol for streaming evidence content into the flow grid.

---

## 1. Purpose and Scope

This module enables multiple users to collaboratively edit a debate round’s flow spreadsheet with consistent conflict resolution, without requiring centralized coordination. It also establishes a bridge communication channel allowing CardMirror to inject research evidence as flow cells in real-time. The architecture is designed to support in-browser collaboration with memory and WebRTC transports, as well as local network collaboration using Tauri.

---

## 2. P2P Collaboration Architecture

### 2.1 CRDT Replica and Operations Model

At the heart of the collaborator lies the `Replica` class, which implements a Conflict-free Replicated Data Type (CRDT) style state container. Its main responsibilities:

- Maintain the **local state** of the flow sheet's grid model.
- Record **operation logs** representing all user edits.
- Synchronize with remote peers by sending/receiving ops.
- Perform **undo-rebase conflict resolution** to merge concurrent edits without losing data.

Each change to the grid—whether cell text edits, metadata updates, or row moves—is wrapped into discrete operation objects. When remote ops arrive, Ebb uses the **undo-rebase strategy**:

1. Locally unacknowledged ops are "undone" to roll back into a common base state.
2. Remote ops are applied over the base state.
3. The local ops are then reapplied in order atop the merged state.

This preserves all edits consistently and respects causal ordering.

The Replica exposes methods to:

- **Generate ops from local grid changes** (`rowOpFromHook()`, `textOpsFromChanges()`).
- **Apply incoming ops** received from peers (`planRemoteApply()`).
- **Record and replay ops locally** (`recordOp()`).
- **Query replica state and metadata**.

This fully encapsulated model manages conflict-free merging and synchronization. The `replica.ts` and `gridOps.ts` modules contain key logic defining these changes and their application.

### 2.2 PeerLink Transport Abstraction

To remain transport-layer agnostic, Ebb defines a `PeerLink` interface that abstracts the network layer used to connect collaboration peers.

There are two main concrete implementations:

| Variant | Usage Context | Technical Detail |
| --- | --- | --- |
| **MemoryLink** | Cross-tab communication within the same browser instance or local tests | Uses in-memory event dispatch without serialization overhead. |
| **TauriLink** | Local network discovery and peer connection on desktop (Tauri) | Utilizes Tauri’s plugin ecosystem to facilitate UDP discovery and WebSocket-like communication over the LAN. |

This abstraction enables Ebb to run smoothly in different environments, reusing the collaboration logic unmodified.

### 2.3 Handshake, Invite, and Presence Protocol

The collaboration session lifecycle proceeds as follows:

- The **user initiates an invite**, which generates an invite code via `createInvite()`.
- The remote peer enters the invite code to establish a connection.
- Peers **exchange handshake messages**, sharing their current **vector clocks/state versions**.
- Both sides calculate missing ops that need to be synchronized.
- Ops are exchanged until both peers converge on identical replica states.
- Throughout collaboration, peers broadcast **presence heartbeats** signaling their current cursor position (selection) and identity.

Presence metadata is visualized in the Handsontable UI using decorations such as colored borders, peer locking indicators, and labels with contact names.

## 3. Presence and Decorations in Handsontable Grid

Peers’ presence is propagated as metadata and rendered in the flow grid UI components (`HotGrid.tsx`). Key features include:

- **Presence Broadcasting:** Each peer periodically publishes their current cursor position and editing state.
- **Claimed Cells:** Cells currently "held" or locked by remote editors are visually distinguished with `LOCK_CLASS`.
- **Peer Decorations:** Colored cell borders and labels show who is editing or present in a cell.
- **Lock Hint Timeout:** When a user tries to edit a locked cell, a brief refusal hint appears (2 seconds).

The core presence management functions include `claimCell()`, `claimCursor()`, and `getPresences()` which integrate peer presence with cell metadata.

Decorations are applied through CSS classes like `PEER_CLASS` combined with initials from peer names and locked state markers.

## 4. Conflict-Free Merge Strategy (undoRebase)

Ebb employs a sophisticated undo-rebase conflict resolution system to merge concurrent edits with minimal data loss:

- When a remote operation is received that conflicts with local unacknowledged changes, the local ops are temporarily undone ("rolled back").
- The remote operation is then applied.
- Finally, the local ops are reapplied (rebased onto the new state).

This process avoids aggressive overwrites and preserves every user’s concurrent input.

Related UI support components include:

- `SharedFlowSyncPanel` React component to present live merge previews and highlight conflicts.
- `FlowEditLogPanel` for logging and viewing flow edit proposals.

Conflict detection functions rely on timestamps and flow argument paths.

## 5. CardMirror Bridge Protocol

The CardMirror Bridge provides a tight integration from the CardMirror editor to the Ebb flow grid, allowing users to send evidence cards or citation snippets into the live flow.

### 5.1 BridgeHost and inbound.ts

`BridgeHost` is the server-side component in the `debate-flow` package that listens for loopback HTTP/JSON requests from CardMirror. It supports two main message types:

- **FlowRequest:** Contains content payloads such as citation text, card IDs, or formatted evidence to insert into a target flow cell.
- **RevealRequest:** Commands the Ebb window to focus or jump to a specific grid location.

The `inbound.ts` module parses and validates these requests before dispatching to the FlowStore or triggering UI actions.

# Summary

The Ebb Collaboration & CardMirror Bridge module provides robust local-first, conflict-free debate flow spreadsheet synchronization between peers without centralized servers. It achieves this through a CRDT-based Replica state model, agnostic peer transport layers, and real-time presence decor. Additionally, the bridge protocol tightly integrates the CardMirror research editor with Ebb, allowing evidence to be sent directly into live flow cells, streamlining the debate preparation workflow.
