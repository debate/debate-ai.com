This page documents the mechanism enabling live cross-tab synchronization across multiple browser tabs or windows, relying exclusively on the browser-native `storage` event and localStorage. This pattern provides timely UI updates without a backend WebSocket or polling infrastructure, ensuring that changes in one tab propagate reactively to all others sharing the same origin.

---

## Overview

The core of the cross-tab synchronization system consists of `live-update.ts` predicate functions paired with storage key sets. Each panel/module defines a set of localStorage keys it depends on and exports a corresponding predicate that inspects the `storage` event's `key` to decide if a reload or data refresh is warranted in the receiving tab.

Browsers invoke the `storage` event **only** in other tabs sharing the same origin, never in the tab which performs the write. Therefore, without this pattern, state updated in one tab would not be reflected immediately in others without reloads.

This mechanism is employed across various packages including `debate-round` (notably its `flow` editor), `debate-search-evidence`, `debate-practice-drills`, and `debate-speech-writer`, forming a uniform cross-tab live-update predicate pattern used throughout the monorepo [packages/debate-round/src/flow/live-update.ts1-40](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-round/src/flow/live-update.ts#L1-L40)[packages/debate-search-evidence/src/state/live-update.ts1-35](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-search-evidence/src/state/live-update.ts#L1-L35)[packages/debate-practice-drills/src/state/live-update.ts1-120](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-practice-drills/src/state/live-update.ts#L1-L120)[packages/debate-speech-writer/src/state/live-update.ts1-76](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-speech-writer/src/state/live-update.ts#L1-L76)

## Data Flow: Cross-Tab Event Cycle

The user initiates an update in one tab ("Tab A") by saving state into localStorage. The browser writes this and then dispatches a `storage` event to all other tabs ("Tab B", "Tab C", etc.) sharing the same origin.

Each listening tab evaluates whether the changed key affects it. If so, it triggers a reactive update, often implemented as a state "tick" increment or explicit data re-derivation.

## Predicate Pattern & Storage Keys

Each package defines a set of localStorage keys backing its panel/store data and exports a predicate function returning `true` if a `storage` event’s key affects the panel.

- The predicates accept a `StorageEvent`-like object with a `.key` property.
- They return `true` if `.key` is either:

- exactly `null` (indicating a `localStorage.clear()` call), or
- exactly one of the known keys the panel cares about.
- Partial string matches are explicitly excluded to avoid unnecessary refreshes.

## Implementation in Components

Panels and hooks implement live update by attaching a `storage` event listener inside a React `useEffect` hook on mount. The handler:

1. Receives `storage` events which fire only from changes in *other* tabs.
2. Calls the package-specific predicate (e.g. `isFlowLiveUpdateStorageEvent(event)`).
3. If `true`, triggers a refresh of panel data. This usually involves:

- Calling state setters to re-read from `localStorage` or persistent stores.
- Incrementing a "tick" state variable (`setViewerTick`) to force React re-renders.
4. The re-render reads updated values directly from localStorage-persistent stores or derives lists/views synchronously.

This pattern enables a single source of truth in localStorage with reactive UI auto-refresh on cross-tab writes.

### The `setViewerTick` Re-derivation Pattern

To minimize unnecessary large data re-fetches or subscriptions, many components use a local state flag, often called `viewerTick`, which increments on relevant `storage` events.

## Flow Spreadsheet & Related Panels Sync

The `FlowSpreadsheet` grid in `debate-round` relies on in-cell badges representing annotations, edits, and prep notes. These badges read directly from localStorage keys like `flowAnnotations` and `flowEdits`. Because widget components like AG Grid cell renderers do not re-render automatically on localStorage changes, the package integrates this cross-tab live update to trigger explicit cell refreshes via:

- A `window``storage` event listener using `isFlowLiveUpdateStorageEvent`.
- On predicate match, calling the AG Grid's `refreshCells({ force: true })` to re-render badges with fresh data.

Similarly, the standalone `FlowEditLogPanel` listens for updates to `flowEdits` and refreshes its editing log interface accordingly.

This closes a longstanding "badges do not update live across tabs" gap [packages/debate-round/src/flow/live-update.ts1-31](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-round/src/flow/live-update.ts#L1-L31)[docs/features/shared-flow-sync.md50-110](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/shared-flow-sync.md?plain=1#L50-L110)

## Viewer-Tick Re-derivation in Practice

The "viewer tick" pattern provides a lightweight way to force components to recompute derived data from persistent stores on cross-tab update events without extra complexity.

### Case Study: CoachingProgramRosterAnalyticsPanel

- Holds internal state variables `programs`, `analytics`, and `challengeDigest`.
- On cross-tab `storage` event for keys like `coachingPrograms`, `groupChallenges`, etc., calls a `refresh()` function.
- The `refresh()` function re-reads from stores (`buildPersistedCoachingProgramNamesAndIds`, etc.) to update state.
- State update triggers immediate re-render with fresh data [packages/debate-contributor-progress/src/panels/CoachingProgramRosterAnalyticsPanel.tsx65-105](https://github.com/debate/debate-ai.com/blob/34937310/packages/debate-contributor-progress/src/panels/CoachingProgramRosterAnalyticsPanel.tsx#L65-L105)

This approach generalizes to many panels, ensuring fresh views synchronized live across all open tabs.

# Summary

The Debate AI codebase implements a uniform cross-tab live-update system that:

- Leverages the browser `storage` event for localStorage change notifications.
- Defines per-panel sets of persistent storage keys and corresponding predicate functions to filter events.
- Installs event listeners in each panel or hook, triggering data re-derivation and React re-render on relevant changes.
- Uses a standard pattern of "tick-increment" state to effect reactive updates.
- Applies this to diverse packages, including debate-round flow editors, evidence research panels, practice drills, and speech writing UIs.

This lightweight, fully client-side approach provides immediate, synchronous UI updates across tabs without backend infrastructure or complex event routing, closing a major Known gap in localStorage-backed panels throughout the monorepo.
