The Crowdsourcing module manages community-submitted research contributions, applying peer review and quality scoring to curate a shared evidence library. This system improves research quality and incentivizes participation via leaderboards and rewards.

## Attributed Contribution System

The core data model is the `AttributedContribution`, which captures a contributor's submission (card, summary, highlight, annotation, original argument, or refutation) along with metadata such as contributor ID, argument block, topic, case area, and word count. Each contribution holds aggregated social signals and quality metrics that feed into blended helpfulness scores used platform-wide [docs/features/contribution-leaderboard.md19-20](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contribution-leaderboard.md?plain=1#L19-L20)

### Scoring and Helpfulness

The system computes a *helpfulness score* blending:

- **Popularity Signals:** Likes and saves tracked with functions like `recordPersistedLike` and `recordPersistedSave`[docs/features/contributions-feed.md53](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L53-L53)
- **Quality Signals:** Arrays of quality ratings and signals gathered from automated assessments or peer reviews [docs/features/contributions-feed.md130-131](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L130-L131)
- **Reviewer Endorsements:** Weighted endorsements, where reviewer credibility strengthens the endorsement's impact. This credibility is computed based on the reviewer's own contribution history, providing diminishing returns for reviewers without an established track record [docs/features/contributions-feed.md71-74](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L71-L74)

Contributions flagged as `isPopularityOnlyOutlier` meet high popularity but low quality, prompting moderation [docs/features/contributions-feed.md17-19](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L17-L19)

### Reviewer Credibility

Reviewer credibility weight is derived from tiered thresholds computed via `computeReviewerCredibility`. New or inactive reviewers receive a minimal default weight (`MIN_REVIEWER_CREDIBILITY`), ensuring endorsement integrity without enforcing fixed roles or permissions [docs/features/contributions-feed.md71-74](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L71-L74)

## Peer Review Lifecycle

Community contributions undergo a structured peer review orchestrated by the `ReviewQueuePanel`. Core to this is the `CardReview` state machine and gating logic ensuring quality control before publication into the shared Evidence Library.

### CardReview State Machine

The review progresses through these statuses with the allowed transitions defined in `ALLOWED_TRANSITIONS`[docs/features/review-queue.md30](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/review-queue.md?plain=1#L30-L30):

| Current Status | Allowed Next Statuses |
| --- | --- |
| `draft` | `in_review` |
| `in_review` | `changes_requested`, `approved`, `rejected` |
| `changes_requested` | `in_review` |
| `approved` | `published` |
| `rejected` | `draft` |
| `published` | (Terminal) |

### Review Guardrails

1. **Blocking Comments:** Review comments marked `blocking` must be resolved before approval can proceed. Unresolved blocking comments block approval [docs/features/review-queue.md22](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/review-queue.md?plain=1#L22-L22)
2. **Permission Tiers:** Critical transitions (`approve`, `reject`, `publish`) require reviewers to meet a minimum tier (`veteran`). This tier is dynamically derived from the reviewer's contribution history using `derivePersistedReviewerTier`[docs/features/review-queue.md108-118](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/review-queue.md?plain=1#L108-L118)
3. **Self-Review Prevention:** Reviewers cannot approve, reject, or publish their own contributions; if the reviewer ID matches the author ID, operations are rejected with a `SelfReviewNotAllowedError`[docs/features/review-queue.md36-37](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/review-queue.md?plain=1#L36-L37)
4. **Library Visibility:** When a `CardReview` exists for a matching `EvidenceLibraryEntry.id`, that entry is hidden from shared library search results unless the review status is `published`. This gating allows controlled publication of community submissions [docs/features/review-queue.md87-89](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/review-queue.md?plain=1#L87-L89)

### Data Flow: Peer Review State Machine

This flow ensures that every review action follows gating rules and lifecycle transitions before mutating persisted storage.

## UI Components & Panels

### Contributions Feed Panel

- Displays a ranked feed of all contributed items sorted by helpfulness score.
- Submission form captures key metadata (argument block, topic, case) and tags, which file contributions into the Argument Library and contribute to topic coverage analytics [docs/features/contributions-feed.md40-45](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L40-L45)
- Actions: Like, Save, and Endorse calls mutate contribution states with safeguards (e.g., no self-endorsement) [docs/features/contributions-feed.md53-120](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L53-L120)
- Moderators can filter to see flagged "popularity-only" outliers to identify potential manipulation [docs/features/contributions-feed.md29-34](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L29-L34)
- Subscribes to cross-tab `storage` events to refresh feeds live across browser tabs [docs/features/contributions-feed.md77-86](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contributions-feed.md?plain=1#L77-L86)

### Contribution Leaderboard Panel

- Aggregates per-contributor statistics computed via `buildPersistedLeaderboardWithCompletedTasks`[docs/features/contribution-leaderboard.md119-140](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contribution-leaderboard.md?plain=1#L119-L140)
- Combines contribution counts, total and average helpfulness scores with tier and streak information derived from progress unlock logic [docs/features/contribution-leaderboard.md130-140](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contribution-leaderboard.md?plain=1#L130-L140)
- Offers range filters (All time, This week, This month) and category filters (Cards, Summaries, etc.) to filter displayed contributors. Contributors with no activity in the filters drop from view [docs/features/contribution-leaderboard.md31-105](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contribution-leaderboard.md?plain=1#L31-L105)
- Includes endorsement history expandable per contributor: received and — if signed in — given endorsements, with inline toggles [docs/features/contribution-leaderboard.md54-78](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contribution-leaderboard.md?plain=1#L54-L78)
- Listens to cross-tab updates to maintain fresh display without reloads [docs/features/contribution-leaderboard.md23-29](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/contribution-leaderboard.md?plain=1#L23-L29)

### Revision Incentives Panel

- Renders a leaderboard rewarding revisions that improve card quality by measured points, rewarding citation strengthening, and outdated evidence replacement [docs/features/revision-incentives.md11-22](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/revision-incentives.md?plain=1#L11-L22)
- Provides a "Stale Evidence Digest" that surfaces cards with citations older than 3 years for targeted revision [docs/features/revision-incentives.md38-42](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/revision-incentives.md?plain=1#L38-L42)
- Includes a recent revisions section with word-level diffs showing before/after changes for argument block, text, and citation fields — diffs are computed from captured snapshots during card edits [docs/features/revision-incentives.md58-72](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/revision-incentives.md?plain=1#L58-L72)
- Subscribes to cross-tab `storage` events to update on revisions and edits performed in other tabs [docs/features/revision-incentives.md106-113](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/revision-incentives.md?plain=1#L106-L113)

### Daily Best Card Challenge Panel

- Each UTC calendar day, identifies the highest-helpfulness score card submitted that day.
- Allows moderators to "Announce today's winner," freezing the day's result to prevent changes by later submissions.
- Shows a calendar heatmap of past announced winners and weekly rollups with the week's champion.
- Every announced winner (and their associated day) supports a comment thread backed by a D1 database table and Next.js API routes for posting and deleting comments.
- Employs local-first accounts syncing to keep comments consistent across devices [docs/features/daily-best-card.md45-58](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/daily-best-card.md?plain=1#L45-L58)
- Listens for cross-tab storage updates to refresh daily best card data in all open sessions [docs/features/daily-best-card.md114-118](https://github.com/debate/debate-ai.com/blob/34937310/docs/features/daily-best-card.md?plain=1#L114-L118)

## Summary

The Crowdsourcing, Contributions & Peer Review subsystem equips the Debate AI platform with structured mechanisms for community research submission, quality improvement, and moderation. Attributed contributions feed into rankings, while an extensible review lifecycle ensures content quality. Gamified incentives and daily challenges foster ongoing engagement, all built atop well-defined local storage and API-backed persistence layers.
