# Tool Data Sync

Account-linked storage for the sidebar's Coaching and Practice tools. What you
save in them — a practice round, a scouted opponent, a judge's ballot history,
a flow annotation, a prep note, a coaching program — is kept on your account
and follows you to another device, instead of living in one browser's
`localStorage` and vanishing the moment you open the app somewhere else.

This closes the "per-browser localStorage, not a shared team resource /
not account-synced" Known gap that [Judge Profiles](judge-profiles.md),
[Opponent Team Profiles](opponent-team-profiles.md),
[Flow Annotations](flow-annotations.md), [Prep Notes](prep-notes.md),
[Coaching Programs](coaching-programs.md),
[Coach Materials](coach-materials.md)' conversation history,
[Pre-Round Briefings](pre-round-briefings.md),
[Practice Round Simulator](practice-round-simulator.md),
[Flow Summaries](flow-summaries.md),
[Judge Paradigm Selections](judge-paradigm-selections.md) and the
[Argument Tree Outline](argument-tree-outline.md) each carried, and extends
the pattern [flows](flow-cloud-save.md), [rounds](round-cloud-save.md),
[word-count rounds](word-count-rounds.md), [drill sets](drill-sets.md) and
[standings](team-rankings.md) already had.

- **Route:** none of its own. The sync runs app-wide; `/settings` → Account →
  **Tool data** is where you can see it (and re-run it).
- **Nav:** the dock's gear-icon menu → "Preferences".
- **Package:** [`debate-data-sync`](https://github.com/debate/debate-ai.com/blob/master/packages/debate-data-sync/README.md)
  (the catalog, the fetch client, the mirror), `apps/debate-ai.com`
  (`/api/tool-records/[collection]`, the `saved_tool_records` D1 table,
  `lib/hooks/useToolRecordSync.ts`,
  `components/layout/ToolRecordSyncProvider.tsx`,
  `components/settings/ToolDataSyncSettings.tsx`). The tool packages
  (`debate-round`, `debate-practice-rounds`, `debate-speech-writer`,
  `debate-team-collaboration`) each call the mirror from their own stores.

`TOOL_RECORD_COLLECTIONS` is an **allowlist**, not a convenience: the route
rejects any collection key not in it, so the table can't be used as a
free-form per-user blob store by a caller inventing names.

The tools already backed by a `saved_*` table of their own — flows, rounds,
word-count rounds, drill sets, judge decisions, strategy recommendations,
coach materials, custom opponent personas, tournament results, sprint
sessions, round pairings — keep those. This is for the stores that had
nothing.

## Local-first, by design

Each tool still reads and writes its own `localStorage` store directly and
stays **fully usable signed out**. The account is a mirror kept up behind it,
not a replacement for it — the same rule every other synced store in this
repo follows ("local apply is never blocked by a sync failure"):

- A local save applies immediately; the upload is fire-and-forget.
- A failed upload is swallowed, never surfaced as a broken save.
- A `401` (a session that expired mid-visit) switches mirroring off rather
  than retrying every subsequent write against an endpoint that will refuse.

## Data flow

```
state/toolRecordCollections.ts  (pure — no fetch, no localStorage)
  → TOOL_RECORD_COLLECTIONS          the allowlist: key, storageKey, idField,
                                       label, href
  → toolRecordId / isSyncableToolRecord
                                     what a syncable record is (an object with
                                       a non-empty string at `idField`) —
                                       shared by the route and the client
  → mergeToolRecords                 local ∪ remote, account wins per id
  → toolRecordsMissingRemotely       the local-only records a sign-in pushes up

state/tool-records-client.ts    (fetch only)
  → listToolRecords                  GET  …/[collection]   (null on 401)
  → saveToolRecordToAccount          PUT  …/[collection]/[recordId]
  → saveToolRecordsToAccount         PUT  …/[collection]   (bulk)
  → deleteToolRecordFromAccount      DELETE …/[collection]/[recordId]
  → clearToolRecordsInAccount        DELETE …/[collection]

state/tool-record-mirror.ts     (the glue the tool stores call)
  → setToolRecordSyncEnabled         off until the app says otherwise
  → mirrorToolRecordSave/Delete/sSave/sClear
                                     fire-and-forget, never throws
  → readLocalToolRecords / writeLocalToolRecords
                                     a collection's store, by storage key
  → hydrateToolRecords               the account merge for one collection

apps/debate-ai.com
  → lib/hooks/useToolRecordSync.ts   enables the mirror for a signed-in
                                       session; reconciles all 13 collections
                                       once per tab
  → components/layout/ToolRecordSyncProvider.tsx
                                       mounts that hook, renders nothing
  → app/api/tool-records/[collection]/route.ts        GET / PUT (bulk) / DELETE
  → app/api/tool-records/[collection]/[recordId]/route.ts   PUT / DELETE
```

### Why one table instead of thirteen

The thirteen stores all have the same shape — a JSON array under one
`localStorage` key, each record identified by one string field — so they share
one `saved_tool_records` table keyed by `(user_id, collection, client_id)` and
one route pair, rather than the file set per feature that
`saved_flows`/`saved_drill_sets`/`saved_tournament_results` each took. `data`
holds the whole record JSON-stringified, mirroring those tables'
blob-column approach: a record is read and written as one unit by the tool
that owns it, and its fields are that tool's business rather than the
table's.

### Why a mirror instead of a hook per tool

These stores are written from all over their packages — panels, hooks, CSV
importers, undo/redo stacks, and one store writing another's (logging a
judge's round rebuilds that judge's derived profile, so one call mirrors into
two collections). Threading an "and also sync it" callback through every one
of those call sites would have been a large mechanical change across four
packages, and every future call site would have to remember it. Instead each
store's own `save*`/`delete*` functions — the one place every write already
funnels through — call `mirrorToolRecord*`.

Two properties make that safe to call from an otherwise pure state module:

- **Off by default.** Nothing syncs until `setToolRecordSyncEnabled(true)`,
  which only `ToolRecordSyncProvider` calls, and only once `useSession`
  reports a signed-in user. A signed-out browser, a server render and a unit
  test therefore make no requests at all.
- **Never throws, never blocks.** A mirror call returns immediately and
  swallows its own failure.

## The merge

On the first page load of a signed-in tab, `useToolRecordSync` reconciles each
collection in turn (sequentially, not thirteen requests at once racing the
page's first paint):

- A record the account has and this browser doesn't is **adopted** locally.
- A record both hold resolves to the **account's** copy — it is the shared
  truth across devices.
- A record only this browser has is **pushed up**, in one bulk request. A
  first sign-in is not a reset: nothing local is dropped.
- A local record with no usable id can't be keyed, so it is left alone rather
  than discarded.

Records are create/replace/delete — never edited field-by-field from two
devices at once — so this is a union rather than a conflict resolution, the
same rule [`useStandingsAccountSync`](team-rankings.md)'s tournament-result
merge follows.

Writing the merged records back to `localStorage` also dispatches a synthetic
`storage` event. The panels already refresh on that event (see each package's
`live-update.ts`), but the browser fires it only in *other* tabs — never in
the one that wrote — so dispatching it by hand is what makes an account merge
show up in the open tool without every panel needing to know this sync exists.

The merge is deduped per tab through a `sessionStorage` stamp with a 10-minute
TTL, because the shell document and each framed dock destination both mount
the provider (a page's tool panels run inside the frame, and the mirror's flag
is module state belonging to whichever document imported the store).

## Seeing it

`/settings` → Account → **Tool data** lists every synced tool with a link to
it and says plainly which state you are in:

- Signed out — "These tools save to this browser only", every row "This
  browser".
- Signed in — rows read "Syncing…" then "Synced", or "Not synced" for a
  collection whose merge failed, plus a **Sync now** button for the case where
  a merge failed or another device has since saved something.

## Known gaps

- Still per-user, not per-team. A squad's judge profiles and prep notes sync
  to the account that wrote them; sharing them across a team would need the
  sharing model `card_shares`/`contacts` use, not just this table.
- No identity/permission check on who may log a round for a judge or against
  a team beyond "it's your own account's data" — the same gap
  [Judge Profiles](judge-profiles.md) and
  [Opponent Team Profiles](opponent-team-profiles.md) already note.
- The merge runs once per tab (10-minute TTL) and on **Sync now**; there is no
  push channel, so a record saved on another device mid-session shows up on
  the next reload rather than live. The synthetic `storage` event covers other
  tabs of the *same* browser only.
- Edit-undo/redo stacks (`judgeRoundRecordEditHistory` and friends) stay
  local: what syncs is the current version of a record, so an undo performed
  on one device is not replayable on another.
- A record over `MAX_TOOL_RECORD_BYTES` (200 KB) is refused by the route with
  a 413. It still saves locally — the cap only bounds what one row may hold.
