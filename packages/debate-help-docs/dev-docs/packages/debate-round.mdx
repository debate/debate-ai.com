# debate-round

FIAT — the live round workspace: the ag-Grid flow spreadsheet, column navigation and
split view, the round setup dialog (tournament, teams, judges, spectators, winner), speech
doc panels, export and history dialogs, and the flow/settings stores behind them.

```tsx
import { DebateFlowPage, useFlowStore } from "debate-round"
```

Composes `debate-timer` for speech timing and recording and `debate-editor` for speech
docs; the flow types themselves live in `src/types/flow.ts`.

## Package layout

Logic lives under `src/`, grouped by role; tests live under `test/`.

```

└── test/             # Vitest suites for the flow and storage helpers
```

## Flow History: Saved to account

`dialogs/FlowHistoryDialog.tsx`'s **Saved to account** tab lists the signed-in user's
`saved_flows` and `saved_rounds` rows (`GET /api/flows`, `GET /api/rounds`). The pure
helpers in `state/savedSummaryFilter.ts` decide what it shows: `filterSavedSummaries`
(search), `sortSavedSummaries` with `SAVED_SUMMARY_SORT_OPTIONS` / `toSavedSummarySort`
(newest, oldest, name — natural, case-insensitive, ties by `clientId`) and
`savedSummaryCountLabel` (`"3"`, or `"2 of 5"` while searching). Remove asks with
`confirm()` before calling `DELETE`, and a failed delete sets the row's status to
`"remove-error"`, which shows a `role="alert"` line. The sort choice is
remembered in `state/savedListSortPreferences.ts` (`getSavedListSort` /
`saveSavedListSort`, surface `"flow-history-saved"`): a JSON array under the
`savedListSortPreferences` key, one `{ id, sort, updatedAt }` record per list surface,
which is a `TOOL_RECORD_COLLECTIONS` entry, so it syncs to the user's
`saved_tool_records` rows. The dialog reads it each time it opens, saves on change
(re-picking the saved order writes nothing), and re-reads on a `storage` event for that
key, which another tab or an account merge dispatches. Unreadable storage or an unknown
sort falls back to `"newest"`. The search box is not remembered.

A failed **Load** sets the row's status to `"load-error"` (kept apart from `"error"`,
which the Rounds tab's save chips read for the same flow ids) and stores
`describeSavedLoadFailure(kind, failure)` in `cloudLoadErrors` / `cloudRoundLoadErrors`:
a `null` from `fetchSavedFlow` / `fetchSavedRound` (a 404 or 401) reads "no longer in
your account", a thrown `Error` shows its message (the route's 422 "damaged … you can
remove it" comes through as is), anything else a generic "try again". The line is a
`role="alert"` under the row and is cleared when the dialog reopens. Loading a saved
round fetches its missing flows with `.catch(() => null)`, so a flow that fails to load
is skipped like one that was never saved instead of failing the whole round.

### Removing a saved round with its flows

A plain `DELETE /api/rounds/[clientId]` touches only `saved_rounds`. With
`?withFlows=1` the route reads every one of the user's saved rounds, takes the
target's flow ids (`readSavedRoundFlowIds` — integer `flowIds` only, so a row
that fails `isValidRound` still counts), and `planSavedRoundFlowRemoval` splits
them into `remove` and `kept` (another saved round of the same user points at
them). It deletes the `remove` flows that are in `saved_flows` (owner-scoped,
50 ids per `IN (…)`), then the round, and answers a `DeleteSavedRoundResult`:
`removedFlowIds`, `keptFlowIds` (both only ids that were saved) and
`flowsUnreadable` (the round's own `data` couldn't be parsed, so no flow was
touched). Another round whose `data` can't be parsed counts as using no flows,
since it can't be opened anyway. Flows go first: if the round's delete then
fails, the round is still listed and loading it skips the flows that are gone.

`deleteSavedRound(clientId, endpoint?, { withFlows })` sends the flag and
normalizes the answer (malformed ids dropped; a bodiless or older-server
answer reads as an empty result). In `FlowHistoryDialog`, after the first
`confirm()`, the dialog fetches the saved round only when the Flows list has
items, counts its flows that are in that list, and asks
`savedRoundFlowsPrompt(label, count)` when there is at least one. A round
that can't be fetched is removed on its own. Removed flows leave the Flows
list, and `describeSavedRoundRemoval(label, outcome, choice)` (choice
`"none"` / `"kept"` / `"removed"`) fills a `role="status"` line under the
Rounds heading, cleared when the dialog reopens.

Known gaps: the reads and deletes are separate statements, not one
transaction, so a round saved from another tab mid-delete may lose a flow it
just started using. Removing a single saved flow still never checks which
saved rounds use it.
