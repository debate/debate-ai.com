Package name `debate-practice-rounds`. Practice and AI round tooling: AI drill generator,
AI coach mode, judge paradigm picker, AI judge decision, opponent persona picker,
word-count speeches, practice round simulator, speech transcript summaries, argument-tree
outline with Kialo-style pro/con map views (d3: tiered tree, sunburst, mind map, bubble
map, sankey), flow annotations, and AI response-outcome charts. Also practice partners (challenges, the
match finder; `src/practice-partners`), the judge pool (`src/judge-pool`), and Online
Challenges (`src/debate-challenges`: async written debates against players or the AI, with
XP, win-streak boosts and trophies) and Topic Sign-ups (`src/topic-signups`: sign up to debate
any listed resolution, find partners, research squads and research notes), whose types, validation, rules and rewards the app's
API routes import by path. Composes `debate-round`,
`debate-speech-writer`, `debate-timer`, `debate-search-evidence`, and
`debate-contributor-progress`.

## Word-count rounds: deleting from the account

`hooks/useWordCountRounds.ts` keeps `/word-count` rounds local-first and, signed in, merges
them with the user's `saved_word_count_rounds` rows (`/api/word-count-rounds`, keyed by
`roundId`). The merge adopts any round only the account has, so a delete the account never
received used to come back on the next merge: the account `DELETE` was fire-and-forget with an
empty `.catch`, and a delete made before the first merge settled was never sent at all.

Every deleted `roundId` now waits in the module-level `pendingAccountDeletes` set until the
account confirms it. The merge leaves pending ids out of the account's list before
`planWordCountRoundMerge`, then deletes them from the account. A failed delete stays pending
and is retried by the next merge (a refocus past the 10-minute TTL, or the next page load).
The hook also returns it as `accountDeleteError` (`buildWordCountDeleteFailureMessage` in
`state/savedWordCountRounds.ts`) with `retryAccountDeletes` / `dismissAccountDeleteError`.
Saving a round under a pending id cancels its delete. Signed out, nothing is sent and the set
is cleared.

`WordCountRoundsPanel` asks before **Clear** and **Delete all history**
(`buildWordCountRoundDeleteConfirm` / `buildWordCountClearAllConfirm`; signed in, the prompt
says the account copy goes too). It shows the failure as a `role="alert"` line with **Try
again** and **Dismiss**, and counts the rounds beside the **Round history** heading.
Tests: `test/useWordCountRounds.test.tsx` ("failed account deletes"),
`test/savedWordCountRounds.test.ts`, `test/WordCountRoundsPanel.test.tsx` and
`test/WordCountRoundsPanel.sync.test.tsx`.

Known gaps: pending deletes live in memory, so a failed delete is forgotten if the tab closes
before a retry. There are no tombstones, so a second device that still has the round locally
pushes it back up on its own merge.

## Judge decision history: account merge and the per-round cap

`hooks/useJudgeDecisions.ts` keeps the AI Judge Decision history local-first in
`localStorage` (`state/judgeDecisions.ts`) and, signed in, merges it once per page load with
the account's rows from `/api/judge-decisions` (the user's `saved_judge_decisions` rows, keyed by
each decision's `id` as `client_id`). `appendJudgeDecision` caps one round at
`MAX_JUDGE_DECISIONS_PER_ROUND` (20) as it grows, but the merge adopts remote decisions one
by one, so two devices that each stayed under the cap for a round used to add up to 40
entries for it, locally and in the account, that nothing ever trimmed.

After adopting, the merge now calls `trimJudgeDecisionsToCap()`, which keeps each round's 20
newest decisions (ties on `generatedAt` keep the smaller `id`, so every device trims the same
ones) and returns the trimmed ids. A trimmed id the account holds is best-effort deleted
there; a trimmed local-only one is never pushed up. If that delete fails, the next page
load's merge trims and deletes it again. Tests: `test/judgeDecisions.test.ts`
(`trimJudgeDecisionsToCap`) and `test/useJudgeDecisions.test.tsx` (merge cases).

The account enforces the same cap. `MAX_JUDGE_DECISIONS_PER_ROUND` and the trim rule live in
`state/savedJudgeDecisions.ts` (`judgeDecisionIdsOverCap`, re-exported for
`trimJudgeDecisionsToCap`), so `PUT /api/judge-decisions/[decisionId]` uses them too: after
the upsert it reads that user's rows for the decision's round, deletes those beyond the 20
newest (in chunks of 50 ids, under D1's bound-parameter limit) and answers
`{ decisionId, updatedAt, trimmedIds }`. `trimmedIds` can hold the saved decision itself when it
is older than the round's 20 newest. A row whose `data` can't be parsed is neither counted nor
deleted. An older client that never trims therefore can't grow a round past 20 in the account.
Tests: `test/savedJudgeDecisions.test.ts` (`judgeDecisionIdsOverCap`) and the app's
`lib/database/__tests__/judge-decisions-round-cap-route.test.ts` (in-memory SQLite).

Known gaps: the route trims only the round it just saved, so a round an older client grew
past 20 stays over in the account until its next save (the next merge on a current client
still trims it locally and deletes the extras). `useJudgeDecisions` ignores the response's
`trimmedIds`; the device drops the same decisions on its next merge.
