# Practice vs AI

The `/versus-ai` round is a Node/TypeScript port of the Go `arguehub` vs-bot
server (`packages/debate-round-practice-ai`, published as
`debate-practice-vs-ai`), kept as reference sources in the package. Persona
data, prompt construction and AI judging come straight from that port. This
note covers what the app layer supplies: persistence.

## The `DebateStore` seam

`debate-practice-vs-ai`'s `./backend` export defines a `DebateStore`
interface and ships `createInMemoryDebateStore` for tests. Everything but
`createDebate`/`getLatestDebate`/`setOutcome` is optional, so a host can start
with bare persistence and add transcripts or scoring later — exactly what
happened here. `apps/debate-ai.com/lib/practice-vs-ai/store.ts` supplies the
Drizzle/D1-backed implementation the `/api/vsbot/*` routes use
(`apps/debate-ai.com/lib/practice-vs-ai/backend.ts` wires the two together).

## Rounds and transcripts

Each round is one row in `practice_vs_ai_debates`, keyed by `user_id`. The
full `DebateVsBotRecord` (history, phase timings, stance, bot level) lives in
the row's `data` JSON blob — the same pattern `saved_flows`/`saved_rounds`
use — with owner, bot, topic, outcome and result lifted into columns so the
round list can be queried without parsing the blob. `saveTranscript` stays
unset: `createDebate`/`appendMessage`/`setOutcome` already keep that blob
current, so a second transcript table would just be a redundant write.

## Signed-out players

The `/api/vsbot/*` POST routes no longer answer 401 when signed out. A guest
plays as the actor `{ userId: "guest", email: "" }` against
`createGuestPracticeVsAiStore` (`lib/practice-vs-ai/store.ts`), which writes
nothing: `createDebate` returns a throwaway `guest_<uuid>` id, `getDebate`
answers such an id with a placeholder record so `/judge` and `/concede`
still score the transcript the client sends, and the gamification hooks are
unset, so a guest round earns no score or badges and has no history.
`GET /api/vsbot/history` still needs a session. Guest turns run on the
caller's own key or the site's shared keys, unmetered, like signed-in turns.

## Gamification

`packages/debate-round-practice-ai/src/backend/gamification.ts` ports the Go
controller's `updateGamificationAfterBotDebate`/
`checkAndAwardAutomaticBadges` as pure functions: `computeGamificationAward`
takes a `{ score, badges, currentStreak }` profile and a result, and returns
the points, badges and new score to apply — the same point values (50/25/10
for a win/draw/loss) and badge thresholds (`FirstWin`, `Novice` at 10,
`Streak5` at a 5-day streak, `FactMaster` at 500) as the Go switch.
`handlers.ts`'s `recordCompletedRound`, which every `/judge` and `/concede`
request runs after storing the round's outcome, does not call
`computeGamificationAward` itself — it hands the round's `{ debateType,
topic, result }` straight to `store.applyGamificationAward`, which is the
only thing that reads the profile and computes the award, and returns it in
the response body so the client can show it. (Earlier, the handler read the
profile and computed the award itself, then handed a `{ points, badges,
newScore }` snapshot to the store to persist — two rounds finishing close
together, separated by the AI judging call, could each compute their award
from the same stale starting score, and the second store write would
silently overwrite the first round's points. There's no longer a parameter
for a caller to pass a precomputed award through at all.)

The app's store persists the result on the signed-in user's `user_settings`
row rather than a separate table, mirroring the account-preferences pattern
`app/api/settings/route.ts` already uses:

- `practiceVsAiScore` (integer) — the running total.
- `practiceVsAiBadges` (JSON array of badge ids) — merged with, never
  replacing, whatever the row already holds, so a repeat badge check never
  drops one earned in an earlier round.
- `practiceVsAiLastPlayedDayKey` (the UTC `YYYY-MM-DD` of the most recent
  scored round) and `practiceVsAiCurrentStreak` (integer) — the dated
  activity log `Streak5` needed. `debate-practice-vs-ai`'s
  `advanceDailyStreak(lastPlayedDayKey, today, previousStreak)` is the pure
  rule: a second round the same day leaves it unchanged, the calendar day
  right after extends it by one, and anything else (first round ever, or a
  missed day) restarts it at 1. The Go original read `user.CurrentStreak` in
  its own badge check but never incremented it anywhere in
  `debatevsbot_controller.go`, so `Streak5` was unreachable there too — this
  isn't a regression the port introduced.

`getGamificationProfile` reads all four columns (defaulting to `0`/`[]`/no
streak when the user has no row yet) and reports the streak via
`currentDisplayStreak`, which reads as the stored value while the last round
was today or yesterday and as `0` once a day has been missed — without
needing a new round played to reset the stored counter first. It is
otherwise unused by the write path now (kept as a capability probe, and for
any host that wants to display a profile): `applyGamificationAward` re-reads
all four columns itself immediately before writing, advances the streak with
`advanceDailyStreak`, and runs `computeGamificationAward` against that fresh
profile, then does a read-then-merge upsert (`insert … onConflictDoUpdate`)
— the score, badge list and streak are always computed from the row's
current value, the same reason `favoriteTools`' star/unstar op reads the
row's current value first.

The scorecard (`packages/debate-round-practice-ai/src/ui/JudgmentPopup.tsx`)
renders the award's points and any newly-awarded badges in a "Round Rewards"
section when the judge response includes one; the concede flow's toast adds
a `(+N points)` note instead, since conceding doesn't show the scorecard.

## Browsing debate history

Every round was already fully persisted (`practice_vs_ai_debates.data`), but
nothing read the list back — a finished round was effectively unreachable
again once the user left the scorecard. `DebateStore` gained an optional
`listDebates(email)` (`packages/debate-round-practice-ai/src/backend/store.ts`),
implemented by both `createInMemoryDebateStore` (filters its in-memory map by
email) and the app's D1 store (`apps/debate-ai.com/lib/practice-vs-ai/store.ts`,
which ignores the `email` argument and reuses the constructor's `userId`
closure, same as `getLatestDebate`) — `SELECT ... WHERE user_id = ? ORDER BY
created_at DESC, id DESC LIMIT 50`, reusing the existing `rowToRecord`
helper so the response carries the full transcript, not just the list
columns.

`createPracticeVsAiBackend` exposes this as a fifth handler, `listDebates`,
which returns an empty list rather than an error when the store doesn't
implement the hook — the same "optional hook, harmless absence" treatment
`recordCompletedRound` gives the gamification hooks. `GET
/api/vsbot/history` (`apps/debate-ai.com/app/api/vsbot/history/route.ts`)
is a thin wrapper: resolve the session, build the backend with `model: null`
(listing never calls the model), call `listDebates`. Unlike the other four
routes it takes no body, so it doesn't go through `withVsBotBackend` (which
always parses one).

The client's `listDebateHistory()` (`packages/debate-round-practice-ai/src/client/index.ts`)
GETs that route with the session cookie, same as the other four calls. The
UI is a new screen, `DebateHistory` (`packages/debate-round-practice-ai/src/ui/DebateHistory.tsx`):
a list of past rounds (topic, opponent, a win/loss/draw/conceded/in-progress
badge derived client-side via `resolveResultStatus`, and the date), each
expandable in place to its transcript. `BotSelection` gained an optional
`onViewHistory` prop that renders a "View Debate History" button when
supplied; `DebatePracticeVsAi` wires it to a `showHistory` flag that swaps
the picker for `DebateHistory` while no round is active.

### Fallacy hints across the history

`DebateHistory` mounts `FallacyFrequencySummary` (`debate-speech-writer/src/ui`,
the same summary the Word Count page uses) above the list once at least one
round has loaded, with no section on an empty list or a load error. Its input
is `practiceDebateUserSpeeches` (`src/ui/history-fallacy-speeches.ts`), memoised
on the loaded rows: only `sender === "User"` messages, labelled
`"<topic> — <phase>"` (falling back to "Practice debate" / "Speech"), newest
round first and transcript order within one. Blank or non-string text and
rows without a `history` array are skipped. Nothing is persisted and nothing
extra is fetched, so the figure covers the `LIMIT 50` rows of `GET
/api/vsbot/history`, not every round ever saved.

## Resuming a round after a reload

`DebateRoom` already kept its own transcript in a
`debate_${userId}_${topic}_${debateId}` localStorage key, restored whenever
it mounts with matching props — but `DebatePracticeVsAi` (the screen the
route renders) only ever learned which round to mount from a plain
`useState`, which a hard reload discards, so the round always fell back to
the picker even though the transcript was still sitting in localStorage.

`packages/debate-round-practice-ai/src/ui/active-round.ts` closes that gap:
`writeActiveRound(userId, started)` mirrors the round's setup (`debateId`,
bot, topic, stance, phase timings — everything `DebateRoom` needs as props)
into a `practiceVsAiActiveRound_${userId}` key when a round starts;
`DebatePracticeVsAi` reads it back with `readActiveRound(userId)` as its
`debate` state's initializer, so a reload mounts straight into `DebateRoom`
with the same props, which then resumes its own transcript as it always
did. `clearActiveRound(userId)` runs on `onExit` (judged or conceded), so a
finished round doesn't keep resuming. Signed-out users share one `_guest`
bucket, the same fallback `DebateRoom`'s own resume key already uses.

## Draft fallacy hints

`DebateRoom` renders `<FallacyHints text={finalInput} />` above the turn box. The
component lives in `debate-speech-writer/src/ui/FallacyHints.tsx` (moved there from
`debate-practice-drills`, which still uses it in `WordCountRoundsPanel`) and wraps the
offline `detectFallacies` heuristic, so this package gains no new dependency edge. It
scans the unsent draft only; nothing is persisted. Tests: `debate-room.test.tsx`
("DebateRoom fallacy hints") and `debate-speech-writer/test/FallacyHints.test.tsx`.

## Coach debrief on the scorecard

Once the decision is revealed, `JudgmentPopup` renders `RoundCoachDebrief`
(`src/ui/RoundCoachDebrief.tsx`) for the user-vs-bot rubric only. It is hidden
before the reveal so the debrief, which quotes the decision, never spoils it.
`DebateRoom` passes `topic` and its transcript (`transcript={state.messages}`).
`buildRoundDebriefInput` (`src/ui/round-debrief.ts`) maps the four phases (both
scores, both reasons), the verdict, and only the lines with `sender: "User"` to
`debate-speech-writer`'s `RoundDebriefInput`.

The prompt and call live in `debate-speech-writer` (`coach/round-debrief-ai.ts`,
`coach/round-debrief-client.ts`), imported from its public entry, so no new
dependency edge. `buildRoundDebriefSystemPrompt(personaId)` appends a
`coach-personas.ts` style (Standard keeps `ROUND_DEBRIEF_AI_SYSTEM_PROMPT`
unchanged). `buildRoundDebriefUserPrompt` clips each speech to
`MAX_DEBRIEF_SPEECH_CHARS` (1500) and stops quoting at
`MAX_DEBRIEF_SPEECHES_CHARS` (6000), noting how many were left out.
`requestRoundDebrief` posts `{ system, messages, maxTokens }` to the existing
`/api/reason-ai` proxy (sign-in and config gates included) and accepts an
`AbortSignal`, which the component aborts on unmount or a newer request.
`JudgmentPopup` / `RoundCoachDebrief` take `requestDebrief` to override the
call in tests.

The coaching style is remembered under the `"practice-vs-ai"` surface of
`state/coachPersonaPreferences.ts`, so it syncs to `saved_tool_records` through
the existing `coachPersonaPreferences` collection with no schema change, and a
`storage` event for that key updates the open picker.

### Saving the debrief with the round

Each debrief that arrives is kept with its round. `DebateVsBotRecord` has an
optional `debrief: RoundDebriefRecord` (`{ personaId, text, savedAt }`), and
`RoundCoachDebrief` takes an optional `saveDebrief(debrief) => Promise<boolean>`
that `JudgmentPopup` passes through. `DebateRoom` wires it to the client's
`saveRoundDebrief(debateId, …)`, which posts to `POST /api/vsbot/debrief`
(`apps/debate-ai.com/app/api/vsbot/debrief/route.ts`, through
`withVsBotBackend` like the other routes) and the backend's `saveDebrief`
handler. The handler trims both fields and answers 400 for a missing
`debateId`, a blank or over-64-character `personaId` or blank text, 413 over
`MAX_ROUND_DEBRIEF_CHARS` (8,000), 404 for a round the caller doesn't own and
500 when the write fails. A store without the optional
`DebateStore.setDebrief` (the guest store) gets `{ saved: false }` without a
lookup, so a signed-out round is never written.

`createPracticeVsAiStore.setDebrief` re-reads the caller's row and rewrites
its `data` blob with the debrief, so there is no schema change: Debate History
(`listDebates`), **Export** / **Export all** (which carry the parsed `data`)
and **Restore from export…** (which spreads the validated record) all carry
it. `isValidDebateVsBotRecord` accepts an optional debrief that passes
`isValidRoundDebrief`, and `rowToRecord` drops a stored debrief that doesn't,
so one bad field never hides the round. A newer debrief replaces the older
one. The component shows the save result under the debrief ("Saved with this
round in Debate History.", "Not saved — sign in…", or a failure line), and a
per-request token keeps a slow older save from overwriting the newest status.
`DebateHistory` shows an expanded round's debrief above its transcript, with
the style badge for any style but Standard (an unknown id shows as Standard).

Tests: `test/round-coach-debrief.test.tsx` (mapping, picker, request states,

(`isValidRoundDebrief`), `test/store-and-client.test.ts` (in-memory

## Judge feedback style

`DebateRoom` shows a **Judge feedback style** picker (toggle buttons,
`aria-pressed`) in its header until the round ends, listing
`debate-speech-writer`'s coaching personas (`coach/coach-personas.ts`:
Standard, Socratic, Devil's Advocate, Fact-Checker). The choice is remembered
under the `"practice-vs-ai-judge"` surface of `state/coachPersonaPreferences.ts`,
so it syncs through the existing `coachPersonaPreferences` tool-record
collection (no schema change) and is independent of AI Coach Mode's and Coach
Materials' choices. The room starts on Standard, reads the saved style after
mount (so the server render matches), saves on each pick, and re-reads on a
`storage` event for the key.

When the round ends, `judgeRound` sends `feedbackStyle` in the
`POST /vsbot/judge` body (`JudgeRequestBody.feedbackStyle`), only for a
non-Standard style, so a Standard request is unchanged. The handler passes it
to `judgeDebate(model, history, feedbackStyle)`, and `constructJudgePrompt`
inserts `judgeFeedbackStyleSection` between the output format and the
transcript: the persona's instructions, scoped to the `reason`,
`congratulations` and `opponent_analysis` texts, with an explicit instruction
to award the same scores and winner and keep the JSON shape. Standard, a
missing id or an unknown one (`resolveCoachPersona`) returns `""`, so the Go
ported prompt goes out byte for byte. The backend imports the pure
`@debate-ai/speech-writer/src/coach/coach-personas` module rather than the
package index, which would pull React into `./backend`; the package already
depends on the speech writer, so there is no new edge. The scorecard
(`JudgmentPopup`'s optional `feedbackStyleName`) notes the style it was judged
in.

The handler stores the style the judge actually used with the verdict:
`resolveCoachPersona(body.feedbackStyle).id` goes to
`store.setOutcome(id, result, { feedbackStyle })` (the optional third
argument, `OutcomeDetails`), so a missing or unknown request id is stored as
`"standard"`. Stores keep it as `DebateVsBotRecord.judgeFeedbackStyle` and
clear it when `setOutcome` is called without one (a concede), so a style never
outlives the verdict it wrote. The D1 store (`apps/debate-web/lib/practice-vs-ai/store.ts`)
now reads the owner's row and rewrites the `data` blob along with the
`outcome` / `result` columns in one owner-scoped update — no schema change;
`rowToRecord` drops a malformed style (`isValidJudgeFeedbackStyle`: non-blank
string ≤ 64 chars). `isValidDebateVsBotRecord` accepts the field, so Export →
Restore keeps it. Debate History shows "Judged in the <name> feedback style"
on an expanded round that has one; rounds judged before it was stored show
nothing.

reaches the prompt, is stored resolved, and is cleared by a concede),
`test/record-validation.test.ts`, `test/store-and-client.test.ts`,

## Restoring a round from an export

Settings → General → **Restore from export…** brings a round back from an
**Export** / **Export all as JSON** file (`restoreOwnSavedData` in
`apps/debate-web/lib/saved-data/saved-data-restore.ts`). The handlers build
every record themselves, so the package ships `isValidDebateVsBotRecord`
(`src/backend/record-validation.ts`) for records that arrive from outside:
string bot / topic / stance fields, a non-blank topic, a `history` of
`{ sender, text, phase? }` capped at `MAX_PRACTICE_DEBATE_MESSAGES` (500), a
`phaseTimings` clock of non-negative seconds and a positive whole-second
`createdAt`. The encoded record is capped at `MAX_SAVED_PRACTICE_DEBATE_BYTES`
(2 MB). `id` and `email` aren't checked; the restore assigns both.

The restore only inserts. It writes a fresh row id, the caller's `user_id` and
email, `created_at` from the record's `createdAt`, and re-derives `result` from
the outcome the way `setOutcome` does, so a hand-edited `result` in the file
can't stick. It skips a round as already in the account when the exported id
is still the caller's, or when the caller has a row with the same topic,
opponent and start second, which is what a second restore of the same file
finds. It never calls `applyGamificationAward`: the round already scored once.

## Known gaps

See the feature doc's Known gaps — the streak gap it used to describe is
fixed. Open here:

- Guest rounds aren't metered per IP, so a signed-out visitor can spend the
  site's shared AI keys as freely as a signed-in one.
- ~~The Coach debrief is not saved with the round (`DebateVsBotRecord` has no
  field for it), so it can't be reopened from Debate History or exported.~~
  **Fixed 2026-11-21:** a signed-in round keeps its latest debrief in
  `DebateVsBotRecord.debrief` (see "Saving the debrief with the round").
  Only the latest is kept; earlier debriefs of the same round are replaced.
- Two debrief saves for one round are not ordered on the server: if an older
  save lands after a newer one, the older text is what Debate History keeps
  (the scorecard's status line still reflects the newest request). Each save
  waits on a fresh AI reply, so this needs a very slow first request.
- The debrief sees the user's speeches but not the opponent's, and not the
  arguments chosen on the setup wizard's Arguments step.
- ~~The style a round was judged in (Judge feedback style) is not stored with
  it, so Debate History and an export show the reasons but not which style
  produced them.~~ **Fixed 2026-11-21:** stored as
  `DebateVsBotRecord.judgeFeedbackStyle` (see "Judge feedback style"). Rounds
  judged before then have no stored style.

## Tests

`packages/debate-round-practice-ai/test/handlers.test.ts` drives the five
handlers against the in-memory store, including that a store without the
gamification hooks omits `gamification` from the response entirely, and that
`listDebates` returns an empty list for a store without that hook.
`test/record-validation.test.ts` covers `isValidDebateVsBotRecord`, and
`apps/debate-web/lib/saved-data/__tests__/saved-data-restore.test.ts` covers
restoring rounds (owner, re-derived result, de-duplication, invalid and
oversized records, and the Export all round trip).
`apps/debate-ai.com/lib/practice-vs-ai/__tests__/store.test.ts` exercises the
D1-backed `getGamificationProfile`/`applyGamificationAward` against a real
in-memory SQLite database (score and badge accumulation across rounds,
de-duplication, per-user isolation, a case demonstrating the lost-update
race is closed: a profile read before either of two sequential awards still
ends with both rounds' points, not just the second, and the streak: five
consecutive simulated days earns `Streak5`, a second round the same day
doesn't advance it, a missed day restarts it at 1, and a lapsed streak reads
as 0 without a write) plus `listDebates` (newest-first ordering, per-user
isolation, empty list). `packages/debate-round-practice-ai/test/gamification.test.ts`
covers `advanceDailyStreak`/`currentDisplayStreak`/`utcDayKey` directly as
pure functions, including a UTC month-boundary carry.
`packages/debate-round-practice-ai/test/store-and-client.test.ts` covers the
in-memory store's gamification (same race-closed case) and `listDebates`,
plus the client's `listDebateHistory` (GET request, session cookie, error
surfacing).
`packages/debate-round-practice-ai/test/history-fallacy-speeches.test.ts`
covers `practiceDebateUserSpeeches`, and `test/debate-history.test.tsx`
("DebateHistory fallacy hints summary") covers the section in the screen:
user speeches only, the empty message, and no section on an empty list or
an error.
`packages/debate-round-practice-ai/test/active-round.test.ts` covers
`active-round.ts`: round-trip read/write, per-user namespacing, the shared
guest bucket, and tolerating a missing, corrupt, or malformed-shape record.
