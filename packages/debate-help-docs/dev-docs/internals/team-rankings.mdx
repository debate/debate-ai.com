# Team Rankings

How `/rank` gets its rows. The table reads the Glicko-2 rankings computed
by the `debate-rankings-sync-data` package; the older `/api/leaderboard` endpoint (TOC
bid list + DebateDrills Elo) is documented below but no longer feeds the
panel.

- **Route:** `/rank`.
- **Package:** `debate-rankings-sync-data` (the ratings), `debate-rankings` (the
  TypeScript loader, plus the panel and the load hooks under `src/leaderboard/`).

The user-facing **Team Rankings** feature page covers what the table shows.

## `debate-rankings-sync-data`

A Python pipeline (`src/main.py`, a clone of
[github.com/debate/debate-rankings](https://github.com/debate/debate-rankings))
replays each tournament in `tournaments/<format>/` through a Glicko-2 model —
rounds at a config's `majors` twice — and writes three CSVs per dataset to
`output/`:

| File | Contents |
| --- | --- |
| `<id>_full_rankings.csv` | Rank, School, Name, Adjusted Rating (μ − 2φ), Deviation (φ), Matches, Rating (μ), Hash, and aff/neg prelim + elim win rates |
| `<id>_field_statistics.csv` | One row of field-wide aff/neg win rates |
| `<id>_rankings.csv` | A trimmed copy (no Deviation/Matches/Hash); unused by the site |

Datasets are `hspf`, `hsld`, `hsld_sepoct`, `hscx` and `cpd`. A win rate
with no rounds on that side is written as NaN — an empty cell — and parsed
to `null`.

The package's TypeScript entry (`js/index.ts`) exports `RANKING_DATASETS`
(labels plus each config's `tournaments` / `majors`) and
`loadRankingDataset(id)`. The CSVs are pulled in with Vite `?raw` dynamic
imports, so each dataset is its own chunk, nothing is copied, and re-running
`src/main.py` is the whole refresh. There is no server round trip: the data
ships with the client bundle.

## The panel

`DIVISION_CONFIG` (`debate-rankings/src/leaderboard/leaderboardUtils.ts`)
maps each division to its datasets — VPF → `hspf`, VLD → `hsld` +
`hsld_sepoct`, VCX → `hscx`, NDT → `cpd`. A division with two datasets gets a
scope switcher. `useLeaderboardData` loads the selected dataset (and still
fetches `/history` for the champion banner); `RankingsTable` renders one
sortable column per CSV field except the raw Rating and Deviation (only the
Adjusted Rating is shown, rounded to a whole number), and `RankingsFieldSummary` the field
statistics and tournament list. The table is shown for the current season
year only, since the datasets carry no season.

### Rank change (+/−)

Both tables have a **+/−** column: places moved since the previous season.
`buildRankChanges` (`leaderboard/rankChange.ts`) maps each current row to
`lastRank − rank`, or `null` ("new") when the key is missing last season.
Teams key on `teamRankChangeKey` (normalized school + names, partners sorted,
so `Smith & Lee` matches `Lee & Smith`); schools on `schoolRankChangeKey`.
The panel loads last season with `usePreviousSeasonDataset` (division tables,
only when `hasExtinctionSeason(datasetId, year − 1)`, so not LD's Sep–Oct slice
or 2015-16) and a second `useSchoolRankingsSnapshot(…, year − 1)` for the
Schools tab, comparing the same scope. The column is hidden until last season
loads, and a failed load just leaves it hidden. It sorts like any column, with
"new" last in either direction.

## School handles

Every school link and stored school key goes through `schoolHandle`
(`profile/rankingProfileHelpers.ts`): `profileSlug` of the name with a
trailing "University" or a leading "(The) University of" dropped, and when
either is dropped, a trailing state tag too (`Yale University (CT)` → `yale`).
Names without that wording keep their tag, so high schools stay apart
(`University School (OH)` → `university-school-oh`). `schoolHref`,
`schoolSlug` (claims) and the school `FollowButton` all use it, so the full
names in college history, NDT results, claims and site news land on the
rankings' short-name page. `canonicalSchoolHandle` maps an older full-name
segment (`emory-university`, `university-of-kansas`, `yale-university-ct`)
onto the handle; `findSchoolEntries` matches either, and `SchoolProfilePage`
`replaceState`s the address to the handle. School page data keyed under an old
slug is found by `storedSchoolSlug` (`apps/debate-web/lib/school-claims/queries.ts`),
which `/api/schools/[slug]`, its members route and `createClaim` call, so an
old claim's owners, logo and roster stay with the page. Tests:
`test/ranking-profiles.test.ts` ("school handles") and
`lib/school-claims/__tests__/queries.test.ts`.

Known gaps: a school followed before handles dropped "University" keeps its
old slug in `profile_follows`, so its Follow button reads unfollowed on the
new handle (the follow still lists and links correctly). "Miami University"
and "University of Miami" share `/@miami`.

## All-seasons NDT points

The NDT + CEDA summary tiles (championships, best finish, elim qualifiers,
elim finish ranks) and their source line are `ProfileNdtHeadline`, exported
from `ProfileNdtHistory.tsx` and rendered by `SchoolProfilePage` in the
header column for college schools; the College NDT record card keeps only the
lists. Both call `useNdtHistory`, which shares one cached load.

`ProfileNdtHistory` (`debate-rankings/src/leaderboard/profile`) puts an **All
seasons** button beside the College NDT record title. It opens
`NdtAllSeasonsDialog.tsx`, a native `<dialog>` (`showModal`, with an
`open`-attribute fallback for jsdom) that builds the table lazily on first open
from the NDT history the card already loaded. `buildNdtAllSeasons`
(`ndtAllSeasons.ts`) scores every team and school from
`data/ndt-school-history.json` with `STRENGTH_WEIGHTS` from `programStrength.ts`
— elims (deepest round per team per NDT, championships merged in as
`Champion`), Copeland, first-round bids and speaker awards — so retuning the
weights there moves the chart and this table together. Each part is then
scaled by `NDT_POINTS_MULTIPLIERS` (elims 1, copeland 1.5, bids 1, speakers 1,
partners 0.25, highSchool 0.5: `E + 1.5C + B + S + 0.25O + 0.5H`); totals and
parts round to two decimals. Every result is also scaled by
`ndtEraMultiplier(year)`: `NDT_PRE_ERA_MULTIPLIER` (0.6) for seasons before
`NDT_ERA_CUTOFF_YEAR` (2000), else 1, applied per result in `score`, in the
per-debater speaker tally and on each high school result's `points`, so side
partnership credit and school totals inherit it. After the base
scores, every partnership of each debater (school + name slug) is grouped;
a team row is kept only when it is the top-scoring partnership of both its
debaters, and it gains `SIDE_PARTNERSHIP_SHARE` (the `partners` multiplier, 0.25) of every
other partnership either debater had, as the `partners` part, listed in
`sidePartnerships`. Each ranked row's debaters are then looked up by
full-name slug in `TOC_RESULTS` (Policy only, `sync/toc-champions.ts`) and
`NDCA_POLICY_RESULTS` (`sync/ndca-champions.ts`, the NDCA's champions and top
speakers from 2006; `buildNdtAllSeasons` takes both lists as its second and
third arguments for tests), scoring `HS_TOC_POINTS` (champion 10, runner-up 6,
top speaker 4) or `HS_NDCA_POINTS` (champion 10, top speaker 4), times the
`highSchool` multiplier, as the
`highSchool` part, listed in `highSchool` with each result's `tournament`
(`"TOC"` / `"NDCA"`) and partner(s). School rows are unaffected. Teams key by school plus
sorted last names (`ndtTeamKey`); bid names drop their `(Rank: n)` suffix
(`cleanTeamName`). A speaker award is credited to a team only when the speaker's
slug matches a debater on exactly one of the school's teams listed that year;
otherwise it scores for the school row alone. Ties share a rank (`rowRanks`)
and sort by titles, then name. The table also carries `strictTeams` (every
partnership with a score, own NDT parts only, no side or high school credit)
and `debaters` (one row per school + debater slug: the sum of their
partnerships' elims, Copeland and bids, their own speaker awards from a
per-debater tally kept while scoring, and their high school results;
`sidePartnerships` lists every partnership with `credit` = its full total).
The dialog's "Rank by" `<select>` (`NDT_RANKING_MODES`: `debaters`, `teams`,
`strict`) picks which list the Teams tab shows; debater rows aren't linked
since there is no debater page. Tests: `test/ndt-all-seasons.test.tsx`.

`ProfileProgramStrength.tsx` exports two components that share one cached
strength table (`loadStrengthTable`, built once from the NDT history, CEDA's
winners and every top-100 season). `ProfileProgramStrengthHeadline` renders in
the school header (`RankingProfiles.tsx`, both the ranked and the
known-but-unranked branch, above `ProfileNdtHeadline`): three rank cards
(latest season, last ten seasons, all time) from `rankProgram`, each with a
`ListOrdered` icon button that opens a native `<dialog>` listing every
program over that span from `rankPrograms` (`programStrength.ts`; same tie
rule as `rankProgram`, ties ordered by name), with a tab per span, a filter
box, 50-row paging and the page's own school highlighted. `ProfileProgramStrength`
is the chart card under **Historical legend** and no longer repeats the rank
cards. Tests: `test/program-strength.test.ts`,
`test/program-strength-headline.test.tsx`.

## Mascot and logo switches

Settings → Preferences has two switches, both on by default
(`debate-webview` `settings/sections/SchoolArtSection.tsx`). They live in

`show-school-mascots` and `show-school-logos` ("0" = off), a same-tab change

Known gaps: pairings already on screen keep their logos until the ratings
reload after the switch flips.

## Rank badge scaling

`TeamRankBadge` (`team-label/TeamLabel.tsx`), shown by `TeamCodeLabel` with
`showRank` on video cards, list rows and the watch page, sizes and colors
itself from the rank through `rankBadgeScale(rank)`. On a log scale from #1 to
#50 (`RANK_BADGE_FLOOR`), the side's blue-600/red-600 is mixed into gray-500
with CSS `color-mix(in oklab, …)` from 100% down to 30%, and the font steps from
12px (#1) and 11px (#2) down to 9px. #1 alone gets a lucide `Crown`, a bold
weight, an amber ring and `data-rank-top`. Ranks past #50 all look the same.
Tests: `debate-videos/test/team-label.test.tsx`.

Known gaps: the fill is an inline style, so it does not switch to the lighter
dark-mode shades the old Tailwind classes used. Browsers without `color-mix`
(pre-2023) fall back to a plain `bg-gray-500` for ranks below #1.

## The legacy `/api/leaderboard` endpoint

Data from `/api/leaderboard?division=<VPF|VLD|VCX>&year=<YYYY>`, served by
[`debate-rankings`](https://github.com/debate/debate-ai.com/tree/master/packages/debate-rankings/src/sync)
(the scrapers and the merge) and `apps/debate-ai.com`
(`app/api/leaderboard/route.ts`, `packages/debate-webview/src/lib/leaderboard/resolve.ts`).

### The two sources

| Source | Gives | Divisions | Fetched from |
| --- | --- | --- | --- |
| TOC bid list | rank, TOC score, bid count, students, state, per-tournament breakdown | CX, PF, LD | `tocbidlist.com/api/enriched-leaderboard` |
| DebateDrills | Debate Elo rating and Elo rank | PF, LD | ranking CSVs on `raw.githubusercontent.com` |

Neither is ours and neither is under contract. They go down separately, and
the current season's table is a join of the two: the bid list is the spine,
Elo is merged onto it.

Prior seasons (2021–2025) are DebateDrills-only — the bid list API serves the
current season — so `/rank` for an older year returns Elo rows for PF and LD
and an empty list for anything else.

### Joining them by name

The two sources name the same team differently, so `mergeElo`
(`packages/debate-rankings/src/sync/merge-elo.ts`) tries progressively more
forgiving keys:

1. Both names normalized — lowercased, punctuation stripped, whitespace
   collapsed — and matched exactly.
2. **LD only:** DebateDrills folds the debater's initials into the team name
   where TOC keeps them in a separate `students` field, so the initials are
   appended before matching (`Harker` + `Ada Lovelace` → `harker al`).
3. **PF only:** partners' initials are not always listed in the same order,
   so a trailing 2-or-3-letter initials block is also tried under every other
   ordering — `Strake Jesuit MS` as `Strake Jesuit SM`, or a 3-initial
   `Strake Jesuit MJS` as each of its other five orderings.

A row that matches nothing is returned **unchanged** rather than dropped: a
partial or empty Elo dataset costs you the Elo column, not the leaderboard.

### Degrading when a source is down

`resolveLeaderboard` (`packages/debate-webview/src/lib/leaderboard/resolve.ts`) owns
this; the route is the HTTP shell around it. Both upstreams are requested
concurrently and what to serve is decided afterwards:

| TOC bid list | DebateDrills | Served |
| --- | --- | --- |
| ✅ | ✅ | merged rows |
| ✅ | ❌ | bid-list rows, no Elo column |
| ❌ | ✅ (non-empty) | Elo-only rows |
| ❌ | ❌ / empty | `502` with `{ error, details }` |

CX has no Elo source, so a bid-list outage is a `502` for that division.

Two rules this encodes, both of which the endpoint previously got wrong:

- **One dead upstream must not take out the other.** A single wrapping
  `try`/`catch` used to answer `500` the moment either scrape threw, so a
  tocbidlist outage blanked PF, LD *and* CX at once even though DebateDrills
  was answering.
- **An upstream failure is a `502`, not a `500`.** The app is fine; something
  it depends on is not. Saying so keeps third-party downtime out of our own
  error rate.

Every failure is `console.error`-logged before it is absorbed, so it lands in
Workers Logs. The DebateDrills branch used to swallow its error in a bare
`catch {}`, which made an outage indistinguishable from a season with no Elo
published yet.

### `grab`, not `axios`

Both scrapers go through `grab-url`, the repo's standard request client.
This matters more than house style: these scrapes run **inside the Cloudflare
Worker**, where `axios` picks its transport at import time and reaches for
`XMLHttpRequest` or `node:http` rather than the runtime's real `fetch`.

`grab`'s `cancelOngoingIfNew` is explicitly **off** for the bid-list fetch. It
defaults on and is keyed by path, which is right in a browser (one user, one
in-flight request per endpoint) and wrong on a server, where two visitors
asking for the same division at the same moment would cancel each other.

`grab` also resolves with an `.error` field instead of rejecting, so both
scrapers check it — an unchecked result looks exactly like a successful empty
response.

## Known gaps

- The +/− column matches teams by exact (normalized) school and debater names,
  so a team that changes partners, or a school whose spelling changes between
  seasons, reads as **new**. LD debaters who switch schools also read as new.
- Both sources are scraped live on every request with no server-side cache, so
  each page load costs two third-party round trips and the endpoint is only as
  fast and as available as they are.
- The name join is exact-match-after-normalization plus two hand-written
  special cases. A school that renames itself mid-season still silently loses
  its Elo column — there is no Fuse.js-style fuzzy fallback for that, and the
  `LeaderboardEntry` simply comes back without `debateElo`.
- ~~A partnership listed with three initials silently loses its Elo column:
  `swapTrailingInitials` only ever tried the one reversal of a two-letter
  suffix.~~ **Fixed:** `trailingInitialsVariants` (same file) generalizes this
  to every other ordering of a 2-or-3-letter trailing initials block — one
  variant for two letters (unchanged), the other five orderings for three —
  so a PF partnership like "Strake Jesuit MJS" still matches "Strake Jesuit
  SMJ" on the other source. A block outside that 2-3 length range still
  doesn't match, same as before.
- `CURRENT_YEAR` is hardcoded. Each new season needs it bumped, or `/rank`
  serves the new year from the historical Elo-only path.
- ~~NDT has no bid-list or Elo data source, so the panel showed only the
  champion banner.~~ **Fixed:** NDT now reads the `cpd` (college policy)
  dataset from `debate-rankings-sync-data`.
- `debate-rankings-sync-data` has no season dimension. The panel shows it for the
  current season year only, and the datasets must be recomputed by hand
  (`python src/main.py`) as tournaments are added.
- `/api/leaderboard` and its scrapers are still deployed but no longer used by
  `/rank`.




## Short answer up front

All three answer the same question — "given who beat whom, how strong is each side?" — and they're not really rivals so much as **the same model at three levels of sophistication**:

- **Bradley–Terry (BT)** = the statistical model (batch fit, maximum likelihood / Bayesian)
- **Elo** = BT solved online, one game at a time, with a fixed learning rate `K`
- **Glicko(-2)** = Elo plus an explicit uncertainty term (and volatility), updated in rating periods

So the real question for debate is: *do you want a streaming number, a number with error bars, or a fitted model you can add covariates to?*

---

## 1. Elo

`E_A = 1 / (1 + 10^((R_B − R_A)/400))`, then `R_A' = R_A + K(S_A − E_A)`

**Unique advantages**
- Dead simple, explainable to a 14-year-old debater, implementable in a spreadsheet
- Updates instantly after each round; no fitting, no matrix algebra
- Zero infrastructure — good for a club ladder or a tab that must never break

**Weaknesses**
- **Order-dependent**: same results in a different sequence → different ratings
- `K` is a fudge factor that conflates "how fast to learn" with "how noisy is this game"
- No uncertainty: a 1500 after 2 rounds looks identical to a 1500 after 60
- Can't express side bias (gov/opp), judge leniency, or topic difficulty without hacks
- Prone to inflation/deflation as the population churns; provisional ratings are crude

---

## 2. Glicko / Glicko-2

Each player carries `(r, RD)` — rating and rating deviation. Glicko-2 adds volatility `σ`, updated per rating period.

**Unique advantages**
- **Uncertainty is first-class.** New and inactive players get wide RDs, so they move fast and settle quickly; veterans move slowly. This is exactly what a debate season needs (a team with 4 rounds shouldn't be ranked as confidently as one with 20)
- `g(RD)` down-weights wins over opponents you don't know much about → better strength-of-schedule behaviour than Elo
- Rating periods make batch updates natural; RD decay handles inactivity honestly
- Output includes confidence intervals → defensible seeding and break predictions

**Weaknesses**
- Still no covariates (no side, judge, or motion effects)
- More complex to explain; the volatility iteration is opaque
- Needs well-chosen rating periods; period boundaries can still create mild order effects
- Assumes one latent strength per team — doesn't know about teams, only individuals

---

## 3. Bradley–Terry

`P(i beats j) = p_i / (p_i + p_j)`, with `p_i = exp(θ_i)` — i.e. a logistic model on strength difference. Fit by MLE (convex, unique up to a shift when the comparison graph is connected) or Bayesian/ridge.

**Unique advantages**
- **Statistically the correct backbone.** Elo is literally online gradient ascent on the BT likelihood — BT is what Elo is approximating
- **Handles unbalanced schedules properly**, which is the norm in debate (teams play different opponents, different sides, different motions)
- **Covariates**: side bias (gov/opp), judge effects, motion/category difficulty, school, experience — all as terms in one model
- **Error bars and hypothesis tests** fall out for free: standard errors, likelihood-ratio tests, CIs
- **Extensible to the formats debate actually uses**:
  - Davidson model → ties / "no result"
  - Plackett–Luce → **British Parliamentary 4-team rankings** (1st–4th), which Elo and Glicko simply cannot represent
  - Thurstone–Mosteller / ordered logit → ordinal placements
  - Hierarchical/random effects → separate true team skill from judge noise
- Regularization/Bayesian priors stop undefeated teams from getting infinite ratings — a real problem in small fields

**Weaknesses**
- Batch, not streaming (though refitting a few hundred teams takes seconds — this is less of a limitation than people think)
- Assumes static strengths unless you add a time-varying/state-space layer
- Needs a connected comparison graph; isolated teams are unidentified
- Least transparent to outsiders — "your rating came from a maximum-likelihood fit" is a harder sell than "you gained 12 points"

---

## Head-to-head

| | Elo | Glicko-2 | Bradley–Terry |
|---|---|---|---|
| Update model | per game | per period | batch fit |
| Uncertainty | ✗ (ad hoc) | ✓✓ core feature | ✓✓ (SE / posterior) |
| Order dependence | high | low | none |
| Strength of schedule | partial | good | correct |
| Side / judge / motion covariates | ✗ | ✗ | ✓✓ |
| 4-team BP rankings | ✗ | ✗ | ✓ (Plackett–Luce) |
| Ties | hack | hack | ✓ (Davidson) |
| Live tab usability | ✓✓ | ✓ | ✓ (refit between rounds) |
| Transparency to debaters | ✓✓ | ✓ | ✗ |
| Implementation effort | trivial | moderate | high |

**Unique advantages in one line each**
- **Elo**: the only one you can explain in a sentence and run in a spreadsheet.
- **Glicko-2**: the only one that treats "we don't know this team yet" as a real, quantified thing while staying incremental.
- **BT**: the only one that can model *why* a result happened (side, judge, motion) and the only one that fits BP's four-way rankings.

---

## Best for debate

**If you want one answer: Bradley–Terry, displayed on an Elo scale.** Convert with `R ≈ 173.7·θ + 1000`, so coaches see familiar-looking numbers while the engine stays statistically honest.

Why BT wins for debate specifically:
1. **Small samples.** A team debates 5–20 rounds a season. You need shrinkage and error bars, not a point estimate — BT with a ridge/Bayesian prior gives exactly that.
2. **Unbalanced schedules.** Teams don't play everyone. BT is built for this; Elo silently misranks.
3. **Side bias is real.** Gov/opp win rates differ by format and by motion set. A single covariate fixes what Elo can only patch.
4. **Judge variance dominates.** Hierarchical BT can attribute noise to judges/pannels instead of dumping it into team ratings — this is the single biggest accuracy gain available in debate tabbing.
5. **BP needs it.** If you run British Parliamentary, you need Plackett–Luce; Elo and Glicko have no representation for a 4-way ranking.

**When to pick something else**
- **Casual club ladder, one person maintains it, no stats background** → **Elo**. A working Elo beats an abandoned BT.
- **Online debate platform with continuous play, players joining/leaving constantly, and you want live numbers with error bars** → **Glicko-2**. It's the best streaming option, and its RD mechanic is genuinely well-suited to sporadic participation.
- **You need break/seeding probabilities next round and nothing else** → Glicko-2 or BT both fine; Glicko-2 is less work.

**A practical hybrid many circuits use:** run BT (regularized, with side + judge + motion terms) after each round or each day, publish ratings on the Elo 400-point scale, and show the CI as a ± next to each number. You get Elo's legibility and BT's correctness.

**Pitfalls regardless of choice:** keep the comparison graph connected, cap or regularize undefeated teams, don't publish rankings before ~5 rounds, and remember that any rating system can be gamed by schedule selection — BT with covariates just makes the gaming visible.
